01プロダクトの概要

Qiita と Zenn から、利用者の興味に合う新しい技術記事を集めて並べる Web アプリです。

画面は https://mytechpulse.net で、API は https://api.mytechpulse.net です。

利用者から見た流れ

  1. 会員登録。 1つ目の画面で、利用者名とパスワードを決めます。2つ目の画面で、興味のあるタグを選びます。候補は100個で、「プログラミング言語」や「クラウド / インフラ」など9つの分類に分かれています。分類ごとにまとめて選ぶこともできます。1個以上選べば登録できます。
  2. 記事一覧。 登録やログインが済むと、記事一覧が開きます。Qiita の記事と Zenn の記事を、それぞれ最大10件、点数の高い順に表示します。
  3. 記事を開く。 記事を押すと、元のサイトが新しいタブで開きます。同時に、その記事のタグの興味が強まり、ほかのタグは少し弱まります。次に一覧を開くと、並びが変わります。
  4. アンケート。 1回のログインの間に、違う記事を3件開くと、アンケートが出ます。最初の質問は「今日のおすすめ記事は役に立ちましたか？」で、1〜5で答えます。2以下を選んだ人には、さらに3つ聞きます。興味に合っていたか、記事が新しかったか、一覧の画面が使いやすかったか、です。

アンケートは、一度出したら60日間は出しません。回答は2年間保存します。回答と一緒に、その時点の興味の上位5タグも記録します。

ログイン後の画面は3つです。記事一覧、マイページ、設定です。マイページには、利用者名と設定へのリンクがあります。記事の保存一覧の置き場所もありますが、中身はまだありません。設定では、パスキーを追加、一覧、名前の変更、削除できます。

判断理由（マイページ）

決めたこと: マイページは、設定ページと別の画面にする。マイページには概要だけを置き、パスキーの管理は設定ページに残す。

理由: オーナーが Issue のコメントで、この案を選びました。

選ばなかった案選ばなかった理由
設定ページと1つにまとめる入口は1つになる。ただし、今ある画面と試験の書き換えが大きいため、初版では採らない。

決めたこと: マイページに出す個人の情報は、利用者名だけにする。

理由: メールアドレス、表示名、登録日は、もともと DB に持っていません。個人情報はできるだけ持たず、出さない方針です。そのため、API と DB は変えずに、今ある「自分の情報」を返す API を使いました。

記事一覧を1回開いたときに通る道

  1. ブラウザは、Cloudflare Pages から画面のファイルを受け取ります。
  2. 画面は api.mytechpulse.net に、記事一覧を JSON で求めます。画面と API はドメインが違うので、Cookie を付けたクロスオリジンの通信になります。
  3. 要求はまず Cloudflare のプロキシに届きます。Cloudflare は、本当の接続元 IP を CF-Connecting-IP というヘッダーに入れて、サーバーへ送ります。
  4. サーバーの入口の Caddy は、送ってきた相手の IP を確かめます。Cloudflare の IP 範囲でなければ、本文なしの 403 を返して終わりです。
  5. Caddy は、同じサーバーの中で動く Go の API に要求を渡します。
  6. API は、DB からその人の興味度を読みます。そのあと、Qiita と Zenn に最大10回、同時に問い合わせます。
  7. 集めた記事を採点して並べ、JSON で返します。詳しくは記事一覧ができるまでに書きます。

Cloudflare の IP 範囲は変わることがあります。そのため、毎週月曜の 12:17 JST に、最新の範囲と設定を比べる点検が動きます。違いがあれば点検が失敗し、オーナーに GitHub から通知が届きます。設定を自動では書き換えません。

03記事一覧ができるまで

記事一覧を開くたびに、サーバーは次の順に動きます。記事を前もって集めておくしくみは、まだありません。

  1. 本人確認。 Cookie のセッションを確かめます。無効なら 401 を返します。
  2. 興味度を読む。 その人が持つすべてのタグの興味度を、DB から読みます。
  3. 上位5タグを選ぶ。 興味度が 0 より大きいタグだけを、大きい順に並べ、先頭の最大5個を使います。行の無いタグは 0 として扱うので、ここには入りません。同じ値のタグは、そろえた名前のアルファベット順で先に来ます。
  4. 同時に問い合わせる。 選んだタグを Qiita と Zenn の両方で検索します。タグが5個なら10回です。タグが5個に満たないときは、Qiita と Zenn に1回ずつ、タグを問わない人気の記事も問い合わせます。タグが4個なら 8 ＋ 2 で10回、1個なら 2 ＋ 2 で4回なので、最大の10回は変わりません。全部を同時に送ります。1回の問い合わせは5秒で打ち切り、全体は8秒で打ち切ります。
  5. 失敗したら1回だけやり直す。 時間切れ、接続の失敗、502・503・504 のときは、0.1秒待ってもう1回だけ送ります。ただし、打ち切りまでの残り時間が足りなければ送りません。429（回数の制限）やそのほかの 4xx では、やり直しません。
  6. 新しい記事だけに絞る。 Qiita は、1タグ20件、最大100件を受け取り、直近5日の記事だけを残します。Zenn は、1タグ5件、最大25件を受け取り、直近14日の記事を残します。Zenn で、タグで見つけた記事に直近14日のものが1件も無いときだけ、古い記事をそのまま使います。人気の記事は、この埋め合わせには使いません。
  7. 重複をまとめる。 同じ URL の記事は1件にまとめ、タグは全部合わせます。
  8. 採点して並べる。 点数の出し方は下の採点のしかたのとおりです。点数が同じなら、新しい記事を先にします。ただし、点数が 0 の記事どうしは、いいね数の多い記事を先にします。
  9. 返す。 Qiita と Zenn を分けて、それぞれ上位10件を返します。

例: Go だけを選んで登録した人

この人の興味度の行は、Go の 10000（1.0）の1行だけです。登録画面のほかの99個のタグには、行がありません。行の無いタグは 0 として扱い、上位5タグには入りません。そのため、上位5タグは Go の1個だけです。

問い合わせは4回です。Qiita と Zenn で Go を1回ずつ検索し、残りの4つの枠の代わりに、Qiita と Zenn で人気の記事を1回ずつ取ります。前は、Go と、8000（0.8）同士の同点から名前順で選ばれた Android、Angular、Ansible、Astro の5タグで検索していました。10回の検索のうち8回が、選んでいないタグに使われていました。

項目前（選ばなかったタグは 8000）今（選ばなかったタグは行なし）
上位5タグGo、Android、Angular、Ansible、AstroGo だけ
問い合わせタグの検索が10回Go の検索が2回と、人気の記事が2回

空いた枠を人気の記事で埋める

興味度が 0 より大きいタグが5個に満たないときだけ、人気の記事を取ります。5個あるときは取りません。取り方は次のとおりです。

提供元取る記事件数
Qiita直近5日に投稿され、ストックが10以上の記事。Qiita の検索には「いいね数の順」の指定が無いので、条件で絞ってから、こちらでいいね数の順に並べます。10件
Zenn技術記事の、週間の人気順。直近14日の記事だけを使います。5件

人気の記事は、タグで見つけた記事と一緒に採点し、Qiita と Zenn それぞれの上位10件に入るかを決めます。決まった数の枠を取っておくのではありません。人気の記事に興味のあるタグが付いていれば、そのタグの値で点数が付きます。付いていなければ点数は 0 で、タグで見つけた記事の後ろに、いいね数の多い順で並びます。

  • Go だけの人の Zenn の列は、Go の記事が最大5件と、人気の記事が最大5件です。合わせて10件以下なので、人気の記事もたいてい並びます。
  • Qiita の列は、Go の記事が直近5日に10件以上あると、点数 0 の人気の記事は上位10件に入りません。
  • Zenn の一覧は記事のタグを返さないので、Zenn の人気の記事にはタグが付きません。
判断理由（空いた枠を人気の記事で埋める）

決めたこと: 興味度が 0 より大きいタグが5個に満たないときは、空いた枠を、全タグの中からの人気の記事で埋める。興味度が 0 のタグは、上位5タグに入れない。オーナーが 2026-10-19 に決めました。

理由:

  • 選ばなかったタグを 0 にしたので、登録の直後は、選んだタグの数しか枠が埋まりません。
  • 人気の記事は、新着の記事より質が安定しています。知らなかったタグの記事に出会うきっかけにもなります。
  • 新しい計算や外部のサービスが要らず、すぐに作れます。
選ばなかった案選ばなかった理由
新着の記事で埋める記事の質が安定しない。
興味度 0 のタグを、アルファベット順で入れる（前の動き）興味と関係のないタグ（Android、Angular など）ばかりになる。
枠を空けたままにする登録の直後に出る記事が少なくなる。
興味のあるタグに似たタグの記事で埋める将来やりたいが、作る手間が大きい。後回しにした。
空いたタグの数に応じて、人気の記事の枠を取っておく（例: タグが1個なら10件のうち8件）選んだタグの記事より、点数 0 の人気の記事を上に出すことになり、「点数の高い順」という1つの決まりが崩れる。
Qiita の人気の記事を、ストックの条件なしで期間だけで取る新しい順に取れるだけなので、投稿直後のいいね 0 の記事ばかりになる。
Qiita の人気の記事を、タグ別と同じ20件、または100件取って並べ替える人気の記事は本文が長い。2026-10-19 の実測で、ストック5以上の20件が約2.3MB になり、応答の上限（約2MB）を超えて取れない。10件なら約1.2MB。

採点のしかた

興味の合計 = 記事に付いたタグのうち、その人が興味度を持つタグの値を足したもの
Qiita の点数 = 興味の合計 × （いいね数 ＋ 1）
Zenn の点数　= 興味の合計（いいね数は使わない）

興味の合計には、上位5タグだけでなく、その人が持つすべてのタグの値を使います。行の無いタグは 0 なので、点数に効きません。たとえば、Go だけを選んで登録し、Go と Docker が付いた記事を1回押した人は、Go が 10000（10000 × 0.8 ＋ 2000）、Docker が 2000 です。この人にとっての点数は、次のようになります。

記事計算点数
Qiita、タグは Go、いいね 3010000 × 31310000
Qiita、タグは Go と Docker、いいね 9（10000 ＋ 2000）× 10120000
Qiita の人気の記事、タグは Android と Kotlin、いいね 800 × 810
Zenn、Go で検索して見つかった記事1000010000
Zenn の人気の記事（タグなし）00

Zenn の記事には、検索に使ったタグを記事のタグとして足しています。Qiita と Zenn は別々の列で返すので、点数の桁が違っても混ざりません。

Zenn にいいね数を掛けない理由は、移行の設計書に「提供元側の並び順を利用するため」とあります。Zenn を呼ぶときに並び順は指定していないので、Zenn の既定の並び順で返ってきます。既定はトレンド順です。2026年10月20日に、並び順を指定しない場合と、トレンド順（その日の分）を指定した場合で同じ5件が同じ順で返ること、新着順を指定した場合とは順番が違うことを確かめました。Zenn に公式の仕様書はないので、この既定は Zenn 側の都合で変わることがあります。

判断理由（空白を含むタグ）

決めたこと: 「Spring Boot」のような空白を含むタグは、表示名を空白のまま残す。Qiita と Zenn に問い合わせるときだけ、空白を除く。Qiita には「SpringBoot」、Zenn には小文字の「springboot」で問い合わせる。

理由: 空白を含むタグでは、Qiita と Zenn の記事が取れていませんでした。表示名、DB、点数の計算は変えずに、問い合わせだけを直す形をオーナーが選びました。

選ばなかった案: 記録なし。

クリックでは、知らないタグを作りません。 クリックを記録する API は、画面から送られたタグ名のうち、タグ表にすでにある名前だけを学びます。タグ表に無い名前は、エラーにせずに無視します。新しいタグも作りません。同じクリックに入っている、ほかの知っているタグは、これまでどおり学びます。名前は、前後の空白を除き、大文字と小文字を区別せずに比べます。
判断理由（クリックで学ぶのは、タグ表にあるタグだけ）

決めたこと: クリックでは、タグ表にすでにあるタグだけを学ぶ。タグ表に無い名前は無視して、新しいタグは作らない。AI の Rex が短期の案の中から提案し、オーナーが 2026-10-21 に取り込んで決まりました。

理由:

  • 以前は、記事に付いていない好きな名前を送っても、タグとして登録できてしまいました。クリックでタグが増えないようにすれば、それを防げます。
  • 無視するだけなので、クリック全体は失敗しません。同じクリックの知っているタグは学べます。
  • 0.8 倍は、送られたタグがすべて知らない名前でも、クリックのたびに行います。
選ばなかった案選ばなかった理由
サーバーが、記事の ID からタグを調べる今は記事を DB に持っていないので、できない。記事を前もって集めた後の、長期の案。
最後に返した一覧のタグを覚えておく新しい状態を持つことになり、再起動で消える。
知らないタグがあれば、リクエスト全体を 422 で断る新しいタグが1つ混ざるだけで、そのクリックの学習がすべて落ちる。
タグの個数の上限を下げる何度も送られれば、タグはそれでも増える。
文字の検査知らないタグを作らないなら、クリックの API では守る意味がほとんどない。意味があるのは会員登録のほうで、別に扱う。
回数の制限上限の値と仕組みを決める必要がある。別の作業にした。その作業は、あとで本番に入りました（回数の制限と入力の文字の検査）。

引き換えに失うもの: Qiita や Zenn に新しく出たタグを、クリックだけでは学べなくなりました。タグ表に足すには、マイグレーションが要ります。あるいは、記事を前もって集めておく形になった後に作る、別の仕組みが要ります。

今のタグ表は、会員登録の画面の100個（DB を作るときに入れたもの）、以前の会員登録で送られたタグ、以前のクリックで作られたタグ、でできています。クリックでも会員登録でも、もう増えません。2026-10-21 の調査では、本番のタグ表には最初の100個のほかに12個ありました。どれも Qiita に実在するタグ（記事から来たもの）で、最初の100個を入れる前に作られていました。悪用の跡は見つかっていません。意味のないタグが残っていた場合に消すかどうかは、オーナーが決めます。

会員登録でも、知らないタグを作りません。 会員登録は、選んだタグがすべてタグ表にあるときだけ受け付けます。1つでも無ければ 422 を返し、利用者もセッションも興味度もタグも、何も作りません。名前は、前後の空白を除き、大文字と小文字を区別せずに比べます。これで、利用者の入力でタグが作られる道はなくなりました。タグ表が増えるのは、マイグレーションで足すときだけです。
判断理由（会員登録では、知らないタグがあれば断る）

決めたこと: 選んだタグの中に、タグ表に無いものが1つでもあれば、422 を返して登録を断る。何も作らない。オーナーの K.Haruki が 2026-10-21 に直すと決め、AI の Rex が実装し、オーナーが 2026-10-22 に取り込みました。使わなくなったタグを作る処理と問い合わせ（同時に作るときの鍵を含む）を消すことも、K.Haruki が 2026-10-22 に決めました。

理由: 会員登録の画面が出すのは、最初の100個のタグだけで、どれもタグ表に入っています。ふつうに画面から登録する分には、断られません。タグは利用者が画面で選んだものなので、黙って落とすと「選んだのに入っていない」ことになります。

選ばなかった案選ばなかった理由
クリックと同じように、知らないタグを黙って無視する利用者が画面で選んだタグです。黙って落とすと、「選んだのに入っていない」ことになる。

画面側だけで検査するJavaScript を書き換えれば、すり抜けられる。
DB の CHECK 制約「表にある名前だけ」は、CHECK では書けない。トリガーは大げさ。

引き換えに失うもの: 古い画面を開いたままだと、タグの一覧がずれて 422 になることがあります。画面には「画面を再読み込みして、タグを選び直してください。」と出ます。

タグの検査は、利用者を作る前の、同じトランザクションの中で行います。そのため、使われている利用者名と、知らないタグが重なったときは、409 ではなく 422 を返します。

04興味の学習

興味度は、タグごとに 0〜1 の値です。DB には、10000 倍した整数（0〜10000）で保存し、計算も整数で行います。

決まり

  • 会員登録で受け付けるのは、タグ表にすでにあるタグだけです。1つでも無ければ 422 を返し、何も作りません。受け付けたときは、選んだタグだけに 10000（1.0）の行を作ります。選ばなかったタグには行を作りません。行の無いタグは 0 として扱います。
  • 記事を1回押すたびに、まず、その人のすべてのタグの値を 0.8 倍します。端数は切り捨てます。
  • 次に、押した記事に付いているタグに 2000（0.2）を足します。上限は 10000 です。
  • 押した記事のタグを、その人がまだ持っていなければ、2000 で新しく作ります。ただし、そのタグがタグ表にすでにあるときだけです。選ばなかったタグは、こうして 0 から 2000 になります。
  • クリックで学ぶのは、タグ表にすでにあるタグだけです。タグ表に無い名前は無視し、新しいタグは作りません。0.8 倍は、どのクリックでも行います。

例1: 同じ種類の記事を続けて押す

Go と React を選んで登録した人がいるとします。行は Go と React の2行だけです。Docker は選んでいないので、行がありません（0）。この人が、Go のタグだけが付いた記事を押していくと、値は次のように変わります。

Docker（選ばなかった）行なし（0）行なし（0）行なし（0）行なし（0）行なし（0）

Go は、0.8 倍して 2000 を足すと 10000 に戻るので、上限のまま動きません。React は、選んだタグなのに、4回で半分以下になります。Docker は押していないので、行ができず 0 のままです。上位5タグは Go と React の2個だけで、残りは人気の記事で埋めます。

例2: 選ばなかったタグの記事を押し続ける

同じ人が、登録の直後から、Docker のタグだけが付いた記事を押していくとします。Go と React の記事は押しません。

1回目で、Docker の行が 2000 でできます。Go と React は 0.8 倍されて 8000 なので、Docker は3番目です。2回目からは、Docker も 0.8 倍してから 2000 を足します（2000 × 0.8 ＋ 2000 ＝ 3600）。3回目は 4880 で、まだ 5120 に届きません。4回目で 5904 になり、4096 の Go と React を追い越します。前の 8000 から始める決まりでは、1回目で 8000 × 0.8 ＋ 2000 ＝ 8400 になり、8000 の Go と React をすぐに追い越していました。

例3: 押さなくなったタグ

10000 のタグでも、そのタグの付かない記事を押し続けると、値は 8000、6400、5120、4096 と下がります。10回で 1072 になります。クリックでできた 2000 のタグも、押さなければ 1600、1280、1024 と下がります。値が 0 になったタグは、行が無いのと同じ扱いで、上位5タグに入りません。

そのほかの決まり

  • 1回のクリックで送れるタグは1〜50個です。1個のタグ名は1〜50文字です。使える文字にも決まりがあります。
  • 同じ人のクリックが同時に届いても、DB でその人の行を押さえて、1件ずつ順に計算します。値が食い違うことはありません。
  • クリックの記録が失敗しても、画面にはエラーを出しません。記事を読む邪魔をしないためです。
  • 送られたタグ名がタグ表に無くても、エラーにはしません。その名前だけを無視して、ほかのタグは学びます。
  • 使えない文字（制御文字や、幅ゼロの空白のような見えない文字、絵文字など）を含むタグ名も、同じように、そのタグだけを無視します。リクエスト全体は断りません。長さの誤りは、これまでどおり 422 です。
  • クリックは、利用者ごとに1分60回までです。一度に20回まで送れ、1秒に1回ぶん戻ります。超えると 429 を返します。画面にはエラーを出しません。詳しくは回数の制限と入力の文字の検査に書きます。
選んだタグが5個より少ないと、登録の直後の上位5タグは、選んだタグの数だけです。名前順で前にある、選んでいないタグが入ることはありません。空いた分は、人気の記事で埋めます。
今いる利用者の値は、まだ直していません。 この決まりが入る前に登録した人には、選ばなかったタグの行（8000 から下がった値）が残っています。直し方はまだ本番にないものに書きます。
判断理由（興味の初期値）

決めたこと: 登録のとき、選んだタグは 1.0（10000）にする。選ばなかったタグには行を作らず、0 として扱う。オーナーが 2026-10-19 に決めました。前は、選ばなかったタグを 0.8 にしていました。

理由:

  • 興味が変わったら、何回かのクリックで、最初に選んだタグを追い越せるようにしたい、というのが前提です。
  • クリックのたびに、選んだタグも 0.8 倍で下がります。そのため、0 から始めても、そのタグの記事を4回押せば、選んだタグ（1.0）を追い越します。上の例2のとおりです。
  • 0.8 という初期値は、根拠の記録が見つかりませんでした。「デフォルト0.8」というメモがあるだけです。
  • 選んだタグの 1.0 は前からの値です。その前は登録のときの値が 1（0.0001）で、1回押したタグ（2000）を大きく下回ったので、尺度の誤りとして直しました。

0（今）4回

回数は、選んだタグの記事を押さない場合です。

選ばなかった案選ばなかった理由
0.8 のまま1回のクリックで選んだタグを追い越し、登録のときの選択がほとんど意味を持たない。同点のタグが、名前順で上位5タグを埋める。
0.1〜0.3 などの小さい値0 と比べて、追い越しが早くなるのはクリック1回分だけ。その一方で全タグの行が必要になり、名前順で上位5タグが埋まる問題がまた起きる。
判断理由（クリックごとの 0.8 倍）

決めたこと: クリックのたびに掛ける 0.8 は変えない。

理由: 意図して決めた値です。新しい行動ほど重く見る、指数移動平均の考え方です。

選ばなかった案選ばなかった理由
0.5 倍過去がすぐに消えてしまう。たとえば 10000 のタグは、関係のない記事を3回押すと、0.8 倍なら 5120 残るが、0.5 倍なら 1250 になる。

05会員登録とログイン

会員登録の流れ

  1. 入力を確かめる。 利用者名は、前後の空白を除いて1〜50文字で、制御文字、見えない文字、改行、タブは使えません。タグは1〜128個で、1個は1〜50文字です。タグに使える文字にも決まりがあり、外れていれば 422 を返します（文字の決まり）。大文字と小文字だけが違うタグは、1つにまとめます。選んだタグがすべてタグ表にあるかも確かめます。1つでも無ければ、422 を返して、何も作りません。
  2. パスワードを確かめる。 条件は4つです。12文字以上であること。72バイト以下であること。利用者名と同じでないこと（大文字と小文字は区別しません）。よく使われるパスワードの一覧（184語）に無いことです。記号や数字を必ず入れる、といった決まりはありません。
  3. まとめて保存する。 利用者、興味度、最初のセッションを、1つのトランザクションで作ります。タグは作りません。タグの検査は、利用者を作る前に、同じトランザクションの中で行います。判断の理由は、記事一覧ができるまでの終わりに書きます。途中で1つでも失敗したら、全部を取り消します。利用者名がすでに使われていたら、409 を返します。
  4. ログイン状態で戻す。 セッションの Cookie を付けて返すので、登録した直後から記事一覧を開けます。

会員登録には、接続元 IP ごとの回数の制限があります。成功も失敗も数えるものと、失敗だけを数えるものの2つです。数値は回数の制限と入力の文字の検査に書きます。

ログインの流れ

  1. 締め出し中か確かめる。 その利用者名か接続元 IP が締め出し中なら、照合する前に 429 を返します。
  2. パスワードを照合する。 bcrypt（コスト12）で照合します。利用者名が存在しないときも、用意したダミーのハッシュと照合して、同じくらい時間をかけます。どちらの場合も、同じ 401 を返します。応答の中身や速さから、利用者名があるかどうかは分かりません。
  3. セッションを作る。 32バイトの乱数をトークンにして、Cookie で渡します。DB には、トークンの SHA-256 だけを保存します。DB の中身が漏れても、そこからトークンは作れません。
  4. ついでに掃除する。 期限の切れたセッションを、ログインのたびに消します。

パスワードの4つの条件は、新しく登録するときだけに使います。ログインの照合には使いません。条件ができる前に短いパスワードで登録した人も、そのままログインできます。

セッションの決まり

  • 有効期限は、ログインした時刻からちょうど24時間です。使っている間に延びることはありません。10:00 にログインしたら、翌日の 10:00 にまたログインが必要です。
  • 本番の Cookie の名前は __Host- で始まります。この名前の Cookie は、ブラウザがほかのサブドメインから上書きさせません。HttpOnly なので JavaScript からは読めません。Secure なので https でしか送りません。SameSite=Lax です。
  • ログアウトすると、その端末のセッションだけを DB から消します。ほかの端末は、ログインしたままです。

ログイン試行の制限

同じ利用者名でパスワードを間違え続けると、しばらく受け付けなくなります。失敗の数え方は次のとおりです。ログイン以外の要求の制限は、次の節に書きます。

  • 失敗は、前の失敗から15分以内に続いたときに数えます。締め出しが明けてから15分間、失敗しなければ、数えはゼロに戻ります。ログインに成功しても、ゼロに戻ります。
  • 利用者名とは別に、接続元 IP ごとにも数えます。1つの IP から、最初の失敗から15分の間に20回失敗すると、その15分が終わるまで締め出します。いろいろな利用者名を試す攻撃を止めるためです。

  • IPv6 は /64 ごとに数えるので、/48 のような大きな割り当てを持つ人は、アドレスを変えて回避できます。
  • 会員登録の失敗が同時に届くと、失敗の上限を少し超えることがあります。それでも、試行の枠（一度に20回まで）で上限は抑えられます。

  • 記録の数の上限で捨てるしくみのせいで、非常に多くのアドレスを持つ人が、自分の記録を押し出せる可能性が、理屈の上ではあります。
  • 学校のような共有の IP から、15分に10回の失敗が出ると、その IP の全員が最長で約90秒待ちます。429 に待ち時間が出ます。
  • 使われている利用者名と一緒にタグを送ると、422 か 409 かで、そのタグがタグ表にあるかどうかが、今も分かります。アカウントは作られません。ただし、調べられる回数は、失敗の枠で抑えられました。
判断理由（回数の制限と文字の検査）

理由: ログイン以外には回数の制限がなく、文字の検査も厳しくなかったためです。アプリの中に置けば、利用者ごとにも数えられ、追加のインフラも要りません。

決めたこと: 会員登録の全体の上限（すべての IP を合わせた上限）は設けない。

理由: 1人の攻撃者が、全員の登録を止められるからです。短い時間に何十件もの怪しい登録が見つかれば、見直します。

決めたこと: クリックのタグに使えない文字があれば、422 にせず、そのタグだけを無視する。

理由: 1つのタグのせいで、そのクリックの学習がすべて落ちるのは避けたいためです。知らないタグの扱いと同じです。

判断理由（会員登録の枠を2つに分ける）

決めたこと: 会員登録は、IP ごとの枠を2つにする。成功も失敗も数える枠は、1時間に60回（一度に20回まで）。失敗だけを数える枠は、15分に10回。2026-10-22 に Rex が決めました。

理由: オーナーの K.Haruki から、学校の Wi-Fi で生徒がいっしょに登録すると、同じ公開 IP になるという心配が出ました。はじめの案は「IP ごとに1時間5回、失敗も数える」で、6人目から止まってしまいます。成功を多めに許し、失敗だけを厳しく見ることで、一斉の登録を通しつつ、利用者名やタグを試す攻撃は止めます。

他のサイトからの悪用を防ぐしくみ（CSRF と CORS）

ログイン状態は Cookie で持つので、別のサイトから勝手に要求を送られると、Cookie が付いてしまうおそれがあります。そこで、データを変える要求には2つの条件を付けています。送り元のページが https://mytechpulse.net であること。X-MTP-CSRF: 1 という専用のヘッダーが付いていること。どちらかが欠けると 403 を返します。ほかのサイトのフォームからは、このヘッダーを付けて送れません。CORS でも、許可する送り元を1つずつ完全一致で決めています。「どこからでも可」にはしていません。

  • ログインと登録には、本人確認（指紋、顔、PIN など）を必ず求めます。

タグ名のそろえ方

タグ名は、前後の空白を除き、小文字にしてから比べます。たとえば「Go」と「 go 」は同じタグです。クリックも会員登録も、そろえた名前でタグ表を探します。クリックは、見つからない名前を無視します。会員登録は、見つからない名前が1つでもあれば 422 で断ります。利用者の入力からタグを作る処理は、どこにもありません。そのため、書き方の違いで同じタグが増えることは、クリックでも会員登録でも、もうありません。タグを足すのはマイグレーションだけです。

表の形の変え方

表の形を変える手順（マイグレーション）は、今は7本です。1本目は、Python 版の頃から使ってきた3つの表と同じ形です。今の DB が同じ形なら何もせず、違っていれば止まります。変更は列や表の「追加」だけと決めていて、試験でも確かめています。理由は技術の選択と理由に書きます。

値を整数で持つ理由

0.8 倍のような計算を小数のまま繰り返すと、保存のたびに誤差が出ます。整数なら誤差が出ず、同じ操作をすれば毎回同じ結果になります。その代わり、0〜10000 からはみ出さないようにする処理と、割り算の切り捨てに気をつけています。

07デプロイと運用

本番のサーバー

  • AWS Lightsail の東京にある、メモリ 1GB のサーバー1台です。費用は月約 $7 です。
  • メモリが小さいので、2GB のスワップを作っています。スワップはなるべく使わない設定（swappiness=10）です。
  • Docker Compose で3つのコンテナを動かします。DB と API は、サーバーの中からだけつながる場所（127.0.0.1）で待ち受けます。外から届くのは Caddy の 80番と443番だけです。443番は HTTP/3 用に UDP でも開けています。
  • Caddy は、Let's Encrypt の証明書を自動で取り、自動で更新します。80番は、証明書を取るときの確認に使うので開けたままです。
  • Caddy は、ブラウザに1年間 https だけを使うよう伝えるヘッダー（HSTS）を付けます。サブドメインも対象です。
  • API のイメージは、Go のプログラム1つだけを入れた最小の形です。root 以外の利用者で動きます。
  • API の説明画面（Swagger UI）を本番で有効にすると、API は起動しません。
  • セッションの24時間、外部への問い合わせの5秒、全体の8秒、応答の 2MiB は、すべて既定値です。本番の設定ではこれらを変えていないので、既定値のまま動いています。

自動デプロイの流れ

main に変更が入ると、人の承認なしで本番に反映します。ただし、変わったのが文書と試験だけなら、反映しません。比べる相手は、最後に反映に成功したコミットです。たとえば 2026-10-20 の main の変更は文書と開発用の設定だけだったので、反映は行われていません。

  1. 検査。 GitHub Actions で、画面、API、設定まわりの検査をすべて通します。1つでも落ちたら止まります。エージェント設定の仕掛けの確認だけは例外で、落ちても止まりません。
  2. 配布物を1回だけ作る。 API のイメージ、画面のファイル、運用のファイル、それらの一覧表を作ります。イメージは GHCR に置き、中身から決まる番号（ダイジェスト）で固定します。同じ番号なら、何度取っても同じ中身です。
  3. サーバーへ送る。 SSH でサーバーへ送ります。ここから先は、サーバーの上のスクリプトが動きます。
  4. 二重に動かない。 鍵を取ります。ほかの反映が動いていたら、何もせずに止まります。
  5. 中身を確かめる。 一覧表の SHA-256 と照らし合わせて、届いたファイルが正しいか確かめます。
  6. 戻し先を記録する。 今動いている API のイメージを、失敗したときの戻し先として記録します。
  7. 新しいイメージを取る。 GHCR から、固定した番号のイメージを取ってきます。
  8. DB をバックアップする。 バックアップを取り、読めるかどうかも確かめます。
  9. 表の形を変える。 マイグレーションを流します。失敗したら、API を入れ替えずに止まります。
  10. API を入れ替える。 新しいイメージで API を起動し直します。死活確認（生きているか、DB につながるか）が通るまで、最大60秒待ちます。
  11. 入口から確かめる。 Caddy を通しても応答が返るかを確かめます。
  12. 失敗したら戻す。 入れ替えか入口の確認に失敗したら、確認なしで、記録しておいた前のイメージに自動で戻します。DB は戻しません。
  13. 画面を公開する。 API の反映に成功したときだけ、画面を Cloudflare Pages に公開します。画面は新しい API に合わせて作られているので、先に出すと古い API と食い違うためです。

判断理由（Cloudflare を通らないアクセスを止める）

理由:

  • その IP は、証明書を取る作業の間の数時間、公開の DNS に載っていました。過去の DNS の記録を集めるサービスに残っている可能性が高く、「見つけにくいだけ」の状態でした。

決めたこと: SQL は手で書き、それを正本にする。sqlc で SQL から型付きの Go のコードを作る。接続には pgx v5 を使う。

理由:

  • 引き換えに、コードの作り直しとマイグレーションの手順を、決まりどおりに守る必要があります。
選ばなかった案選ばなかった理由
GORM検討のときに候補に挙がっている。選ばなかった理由の記録はない。

表の形の変え方（goose と「追加だけ」）

ログイン状態の持ち方（サーバー側のセッション）

決めたこと: ログイン状態は、サーバーの DB に持つセッションで管理する。ブラウザには HttpOnly の Cookie でトークンを渡す。Python 版の JWT はやめる。

理由:

  • Python 版は、JWT をブラウザの localStorage に入れていました。localStorage は JavaScript から読めるので、画面に悪いスクリプトを入れられると、トークンを盗まれます。HttpOnly の Cookie なら、JavaScript からは読めません。
  • DB にあるセッションは、行を消せばその場で使えなくなります。ログアウトしたときの無効化が、サーバーの側で確実にできます。
  • 引き換えに、要求のたびに DB を読みます。画面と API のドメインが違うので、CSRF への対策も要ります。対策の中身は会員登録とログインに書きました。
  • 切り替えのときは JWT を引き継がず、全員に一度だけログインし直してもらいました。パスワードのハッシュは同じ bcrypt のコスト12なので、そのまま使えました。

選ばなかった案: JWT を使い続ける案です。理由は上のとおりです。

エラーの返し方（HTTP ステータスと Problem Details）

決めたこと: 結果は HTTP ステータスで返す。エラーの本文は Problem Details（RFC 9457）の形にする。

理由:

  • Python 版は、本文の中の番号で結果を伝えていました。この方式で、会員登録のときに「名前の重複」と「サーバーの障害」を見分けられない不具合が起きました。
  • その修正の途中で、オーナーが全部の API を HTTP ステータスで返す形に作り替えると決めました。その不具合の修正だけは、当時の番号の方式に合わせて直しました。
  • HTTP ステータスを選んだ理由は2つ書かれています。長い目で見るとこちらが標準的なこと。画面の側で「応答が成功したか」を見る書き方と相性が良いことです。
  • 当時も、ログインの確認（401）だけは HTTP ステータスで返していました。それを全体に広げる、という位置づけです。
  • 本文の形は、Huma が標準で使う Problem Details を基にし、変わらない業務用のエラーの名前（たとえば利用者名の重複）だけを足しました。予想していない内部のエラーの中身は、利用者に返しません。
  • Problem Details の形そのものを選んだ理由は、どこにも記録がありません（理由の記録なし）。
選ばなかった案選ばなかった理由
本文の中の番号で返す（Python 版）「名前の重複」と「サーバーの障害」を見分けられない不具合が起きた。

作業は、表の形の変更（マイグレーション）ではなく、運用の作業として1回だけ行います。手順は、読み取りだけの確認、専用のバックアップ、オーナーの承認、1回だけのスクリプト、対象が0件になったことの確認の順です。スクリプトは用意してありますが、まだ流していません。

判断理由（方針は決定済み）

決めたこと: 今いる利用者の、一度も押していない、選ばなかったタグの行も消して、新しい決まりにそろえる。オーナーが 2026-10-19 に決めました。

理由:

  • 消さないと、今いる利用者（特にクリックの少ない人）は、同点のタグが名前順で上位5タグを埋めるままになります。
  • 消す行は、1人の中ではすべて同じ値です（クリックのたびに 8000、6400、5120… と同じように下がる）。並び順の情報は失われません。
  • 2万人分の試算で、誤って消した行も、消し漏れも0件でした。
  • 手元の試験用の DB（400人、クリック回数はランダム）の試算では、上位5タグが変わる人は、クリック0回で65人中65人、1〜3回で104人中18人、4回以上で191人中0人でした。本番の DB は見ていないので、数字はすべて試算です。
  • バックアップは7日分で、同じディスクにあります。元に戻すには DB 全体を戻すしかないので、消す直前に専用のバックアップを取って残します。
選ばなかった案選ばなかった理由
新しく登録する人だけに新しい決まりを使う今いる利用者に問題が残る。利用者によって学習の動きが変わり、ほかの機能の値も決めにくくなる。
マイグレーションで消す表の変更は追加だけ、という決まりに反する。マイグレーションは自動デプロイで流れ、巻き戻せない。
押したことのある、選ばなかったタグからも、0.8 から始まった分を差し引く選んだタグかどうかの記録が無く、上限で止まる計算もあるので、正確に差し引けない。

決めたこと: 値の尺度を直す前に登録した人のうち、一度もクリックしていない人だけ、選んだタグを 1.0 に直す。

理由: その人たちは、選んだタグが 1（0.0001）のまま保存されています。一度も押していない人は、値がすべて 1 のままなので、確実に見分けられます。クリックしたことのある人は、すでにクリックで学習が進んでいます。

選ばなかった案選ばなかった理由
クリックしたことのある人も含めて、選んだタグを 1.0 に上げるクリックで学んだ興味より、登録のときの選択が上に来てしまう。学習の結果を壊す。
全員そのままにする一度も押していない人は、選んだタグが効かないままになる。
