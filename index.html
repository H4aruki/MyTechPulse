01プロダクト一言

Qiita と Zenn から、利用者の興味タグに合う新しい技術記事を集めて並べる、パーソナライズ技術ニュースWebアプリ。

  • 利用者は、登録のときに興味のあるタグを選びます。
  • 記事一覧を開くたびに、興味の強い上位5タグで Qiita と Zenn をその場で検索します。
  • 結果は点数の高い順に、提供元ごとに最大10件を表示します。
  • 記事をクリックすると、その記事のタグの興味が強まります。ほかのタグは少し弱まります。こうして、直近の関心に寄っていきます。
  • 公開URLは、画面が https://mytechpulse.net、API が api.mytechpulse.net です。
  • ログイン後の画面は3つです。記事一覧 /app/articles、マイページ /app/mypage、設定 /app/settings です。
  • マイページ（#238）には、利用者名と、設定へのリンクがあります。設定では、パスキーを管理します。
  • 記事を開いた利用者向けのアンケート（利用者フィードバック、/api/v1/user-feedback/*）も動いています。
判断理由（マイページ）

決めたこと: マイページは、設定ページと分ける（案B）。マイページには概要だけを置き、パスキーは設定ページに残す。

理由:

  • #235 でオーナーが決め、#238 で実装しました。
選ばなかった案選ばなかった理由
設定ページと統合する入口は1つになる。ただし、既存の画面と試験の変更が大きいため、初版では採らない。

決めたこと: マイページに表示するのは、利用者名だけにする。

理由:

  • メール、表示名、登録日は DB にありません。
  • 個人情報はできるだけ持たず、出さない方針です。
  • API と DB は変えていません（auth/me を使います）。
  • 記事の保存一覧は、場所だけを用意しました。中身は #236 で作ります。

画面（React・TypeScript・Vite・Tailwind CSS）

決めたこと: 画面を React 19.2、TypeScript 6.0、Vite 8、Tailwind CSS 4（@tailwindcss/vite）で作る。

理由:

  • 出典は #48 です。作業記録（2026-07-11）でも確認しました。
  • 旧版は素の HTML と JS で作っていました。画面の重複、型が無いこと、手書きの DOM 操作、状態管理が散らばっていることが負債になっていました。
  • React は、機能を足しながら育てていく前提で選びました。エコシステムの厚みを重視しました。
  • TypeScript を入れたのは、旧版の「本文の status 番号」の意味を型で表せなかったためです。そのため、画面と API のずれを見つけられませんでした。
  • Vite を入れたのは、ビルドをしない運用から抜けるためです。接続先 URL の直書きを、環境変数に置き換えます。公開ページと /app/ を、1つのビルドで両立させます。
  • Tailwind CSS は、UI の刷新と同時に入れました。#48 の時点では shadcn/ui を使う案もありましたが、実装では見送りました。
選ばなかった案選ばなかった理由
Next.js / Nuxt中核はログイン後の画面なので、SEO が要らない。SSR 用の Node サーバーが増え、運用の負担が上がる。
Vue 3移植は楽。ただし、エコシステムの厚みで React を優先した。
Svelteエコシステムと情報量で劣る。
素の JS のまま改善する型や部品化の恩恵がなく、同じ負債がまた生まれる。

画面の切り替え・データ取得・入力フォーム

決めたこと: TanStack Query 5、React Router DOM 7、React Hook Form 7 と zod 4（@hookform/resolvers）を使う。

理由:

  • 出典は #48 です。作業記録（2026-07-11）でも確認しました。
  • 旧版の困りごとに、1つずつ対応させて選びました。
  • React Router は、ページ単位の遷移を、画面の中での切り替えにするためです。
  • TanStack Query は、各所に散っていた fetch の手書きを1つにまとめるためです。キャッシュ、読み込み中の扱い、401 の扱いも一緒にまとめます。
  • React Hook Form と zod は、登録の2段階の画面と入力の検証を、型付きで行うためです。

選ばなかった案: 記録なし。

画面の検査

決めたこと: oxlint、Vitest 5 と Testing Library を使う。openapi-typescript で API の型を作り、その差分を CI で調べる。

理由:

  • API の約束と画面の型がずれたら、CI で止めるためです（AGENTS.md）。
  • CI を入れたとき（作業記録 2026-08-27）、oxlint はすでに入っていました。それを CI から呼ぶ形にしました。
  • Vitest は、カバレッジの計測を内蔵しています。外部サービスに登録しなくても、結果を出せます。

選ばなかった案: ほかの候補と比べた記録はありません。

API（Go と Huma）

決めたこと: API を Go 1.26.4 の標準の HTTP サーバーと Huma v2 で作る。OpenAPI はコードから作る。Python から移し、2026-10-07 に本番を切り替えた。

理由:

  • 出典は ADR 0001 です。堅牢性、保守性、運用の単純さ、将来のチーム開発を両立するためです。
  • Huma v2 は #117 で採用を決めました（2026-09-14 にオーナーが承認）。型付きの HTTP ハンドラー、OpenAPI 3.1 の生成、Swagger UI のためです。
  • Huma には、Go 1.22 以降の標準の http.ServeMux 用のアダプター（humago）があります。そのため、ほかの HTTP ルーターに頼らずに済みます（#117）。

選ばなかった案: #60 では、Web の候補として net/http、Echo、Gin が挙がっています。Echo と Gin を選ばなかった理由の記録はありません。

DB アクセス（pgx と sqlc）

決めたこと: pgx v5 と sqlc を使う。SQL から型付きのコードを作る。

理由:

  • 文書には「SQLを書き、型付きコードを自動生成」とあります。
  • #117 で、手書きの SQL を正本にし、sqlc で型を付けると決めました（2026-09-14 にオーナーが承認）。
  • sqlc は、PostgreSQL 向けの Go の生成を安定版として扱っています。接続には pgx/v5 を選べます（#117）。
  • sqlc の rename の設定を使うと、既存の列名 user_ID と tag_ID を、Go 側の UserID と TagID に対応させられます（#117）。
  • sqlc は、goose の形式のマイグレーションのフォルダを読めます。そのため、スキーマの定義を二重に管理せずに済みます（#117）。
  • DB は PostgreSQL 17 なので、ドライバは pgx にします。sqlc による型の生成も、PostgreSQL 向けが最も充実しています（#60、#63）。
  • #117 には、引き換えになる点も書かれています。sqlc の生成とマイグレーションの手順を、チームで守る必要があることです。
選ばなかった案選ばなかった理由
GORM#60 で候補に挙がっている。選ばなかった理由の記録はない。

認証（サーバー側のセッションとパスキー）

決めたこと: サーバー側のセッション（HttpOnly Cookie）と bcrypt を使う。パスキーには go-webauthn/webauthn v0.18 を使う。

理由:

  • セッションの出典は ADR 0002 です。XSS が起きたときに読まれる範囲を小さくするためです。サーバー側で確実に失効させるためでもあります。
  • パスキーの基盤は #216 で決め、#219 で入れました。
  • 初版では、パスワードと併用します。discoverable なパスキーにします。上限は10件です。
選ばなかった案選ばなかった理由
パスキーを自前で作る検証の漏れが起きる危険が大きい。

エラーの形式（HTTP ステータスと Problem Details）

決めたこと: エラーは HTTP ステータスで返す。本文は Problem Details（RFC 9457）の形にする。

理由:

  • HTTP ステータスで返す方針の出典は #14 です（作業記録 2026-07-09）。
  • 旧 Python 版は、本文の status 番号で結果を返していました。この方式では、登録のときに「名前の重複」と「サーバーの障害」を区別できない不具合が起きました。
  • その修正の途中で、オーナーが全 API を HTTP ステータスで返す形に作り替えると決めました。
  • ただし、その修正（#13）自体は、status 番号の方式にそろえて直しました（#14）。
  • #14 には、HTTP ステータスの方式を選ぶ理由が2つ書かれています。1つ目は、長い目で見るとこちらのほうが標準的なことです。2つ目は、画面側のエラー処理（res.ok を前提にした書き方）と相性が良いことです。
  • 当時も、JWT 認証まわりだけは HTTP ステータス（401）で返していました。移行は、この形を全体に広げる作業だと #14 に書かれています。
  • 本文の形は #117 で決めました。Huma が標準で使う RFC 9457 の Problem Details を基にし、安定した業務エラーのコードだけを足します。予期しない内部エラーの詳細は、利用者に返しません。
  • ただし、Problem Details の形を選んだ理由そのものは、文書、Issue/PR、作業記録のどれにもありません（理由の記録なし）。
選ばなかった案選ばなかった理由
本文の status 番号で返す（旧 Python 版）「名前の重複」と「サーバーの障害」を区別できない不具合が起きた。

HTTPS の終端と入口の制限（Caddy）

決めたこと: Caddy 2 で HTTPS を終端する。証明書は自動で取得し、更新する。Cloudflare の IP 以外からの要求には 403 を返す（#218）。

理由:

  • Caddy の出典は #34 です。作業記録（2026-07-16 と 08-23）でも確認しました。
  • 証明書の取得と更新が、完全に自動です。設定は、ドメイン名を書く数行で済みます。セキュリティ用のヘッダーも、まとめて付けられます。
  • 直接のアクセスを止める方法は #74 で決めました。
  • Caddy の許可リストは #218 で main に入りました。
  • Lightsail のファイアウォールを手作業で絞る作業は、まだ残っています（Issue は OPEN）。
選ばなかった案選ばなかった理由
Nginx + certbot情報量や実績は多い。ただし、証明書の更新を定期実行する管理が要り、設定も長くなる。
Cloudflare Tunnel（#74）1GB のメモリと複雑さを考えると、過剰だと判断した。

CI/CD（GitHub Actions と GHCR）

決めたこと: GitHub Actions（ci.yml、release.yml など）を使う。イメージは GHCR に置く。

理由:

  • #34 では、採用する案として GitHub Actions の名前が挙がっているだけです。
  • #60 では、ビルドをサーバーの上で行わず、GitHub Actions で作って GHCR に置く案が挙がりました。サーバーでの pip install によるメモリの急増を、本番からなくせるためです。#54 の自動デプロイとも相性が良いと書かれています。
  • #117 で、CI で一度だけ作った Go のコンテナを GHCR に保存すると決めました（2026-09-14 にオーナーが承認）。コミットの SHA とダイジェストで固定し、リハーサル、本番、切り戻しに同じものを使うためです。
  • GitHub Actions や GHCR を、ほかの候補と比べた記録は見つかりませんでした。
  • カバレッジは外部サービスに送らず、Actions の実行結果の要約欄に出します。外部サービスへの登録が要らないためです（作業記録 2026-08-27）。今は PR へのコメントにも出しています。

04ドメインモデル

テーブル意味

05おすすめの流れ（GET /api/v1/feed 1リクエストごと）

  1. 本人確認。 セッションの Cookie を auth.Authenticate で確かめます。失敗したら 401 を返します。
  2. 興味度を読む。 その利用者の recommend の行をすべて取得します。正規化すると同じ名前になるタグがあれば、エラー（500）にします。
  3. 上位5タグを選ぶ。 値の大きい順に並べます。同じ値なら、正規化したタグ名の昇順にします。その先頭の5件を使います。
  4. 並列に取得する。 5タグと Qiita・Zenn の組み合わせで、最大10個の goroutine を動かします。結果は、バッファ付きの channel ですべて集めます（errgroup は使っていません）。全体の期限は FEED_TIMEOUT で、既定は 8秒です。外部への1回の問い合わせの期限は PROVIDER_TIMEOUT で、既定は 5秒です。
    Qiita は /api/v2/tags/{tag}/items?page=1&per_page=20 を、Bearer トークンを付けて呼びます。Zenn は /api/articles?topicname={tag}&count=5 を呼びます。
  5. 検証して、期間で絞り込む。 記事を1件ずつ検証します。Qiita は直近5日以内の記事だけを使います。Zenn は直近14日以内の記事を使います。Zenn が0件のときだけ、古い記事で補います。このとき、追加の問い合わせはしません。Zenn の記事には、検索に使ったタグを記事のタグとして足します。
  6. 重複を除く。 URL ごとにまとめます。タグは、重なった記事のタグをすべて合わせます。
  7. 採点して並べる。 点数は、下の採点式で出します。点数の高い順に並べます。同点なら、公開日時が新しい順、提供元、URL の順で決めます。
  8. まとめて返す。 qiita_articles（最大10件）、zenn_articles（最大10件）、warnings を返します。片方の提供元だけが失敗したら、成功した側を返し、warnings に provider_unavailable を入れます。両方が失敗したら、503 を返します。

採点式

興味合計 = Σ（記事タグのうち、利用者が recommend に持つタグの match_int）
Qiita の点数 = 興味合計 × (likes + 1)
Zenn の点数　= 興味合計（いいね数は掛けない）

興味合計には、上位5タグだけでなく、利用者が持つすべてのタグの重みを使います。

Zenn の点数に反響を掛けない理由は、README にあります。「取得時点で提供元のトレンド順に絞り込まれているため重ねて数えない」という説明です。ただし、コードで Zenn を呼ぶときに渡すのは topicname と count だけです。並び順を指定する値は渡していません。Zenn 側の既定の並び順は未確認です。

判断理由（取得まわり）

決めたこと: 空白を含むタグ（例: Spring Boot）は、表示名を空白のまま残す。Qiita と Zenn に問い合わせるときだけ、空白を除く。表示名、DB、順位付けは変えない。

理由:

  • きっかけは、空白を含む興味タグで、Qiita と Zenn の記事を取得できなかったことです（#206 の題名）。
  • #206 でオーナーが決め、#208 で実装しました。

未解決の問題（決定前）:

  • クリックの API で、任意のタグを新しく作れてしまう問題があります（#239、OPEN）。
  • 短期の案は3つです。既存のタグだけを受け付けること、文字の種類を検査すること、回数を制限することです。
  • 長期の案は、#66 の後に article_id を基準にすることです。

07認証

セッション（ADR 0002）

  • ログインか登録に成功すると、32バイトの乱数トークンを発行します。トークンは Cookie で渡し、DB には SHA-256 だけを保存します。
  • 有効期限の既定は24時間です（SESSION_TTL）。
  • Cookie の名前は、本番では __Host-mtp_session、開発では mtp_session です。本番の Cookie は HttpOnly、Secure、SameSite=Lax、Path=/ です。
  • ログアウトすると、その端末のセッションの行だけを消します。ほかの端末のセッションは残ります。
  • 期限切れのセッションは、ログインのたびに掃除します。
  • CSRF 対策として、/api/v1/ の更新系の要求には2つの条件があります。許可した Origin からの要求であることと、X-MTP-CSRF: 1 ヘッダーがあることです。
  • CORS も、許可したサイトだけに限っています。
  • 旧 Python 版の JWT（localStorage）は引き継ぎません。切り替えのときに、一度だけログインし直してもらいます。

パスワード

  • bcrypt のコストは12です。旧 Python 版（Passlib）と同じなので、既存の $2b$ のハッシュをそのまま検証できます。上限は72バイトです。
  • 存在しない利用者でも、ダミーのハッシュと照合します。応答は区別しません。どちらも invalid_credentials の 401 です。
  • 新しいパスワードには3つの条件があります。12文字以上であること、利用者名と同じでないこと、よく使われるパスワードの一覧に含まれないことです。
  • 文字の種類の決まりはありません（NIST SP 800-63B）。この条件は、ログインの照合には使いません（#217）。
  • ログイン試行の制限は、プロセス内のメモリで持ちます（#217）。
  • 利用者名ごとに、15分に5回失敗すると締め出します。締め出す時間は1分、2分、4分と倍になり、最大15分です。
  • IP ごとに、15分に20回失敗すると締め出します。
  • パスキーのログインの開始は、IP ごとに15分に60回までです。
  • IP は CF-Connecting-IP から読みます。本番で CLIENT_IP_HEADER が空なら、起動しません（#231）。

パスキー（WebAuthn）

  • 設定画面で、登録、一覧、名前の変更、削除ができます（#221）。
  • パスキーでのログイン（#228）と、自動入力の conditional UI（#229）もあります。
  • ログインでは、利用者名を入れずにパスキーを選んでもらいます（allowCredentials は空）。
  • チャレンジには、使い捨てのトークンを使います。トークンは応答の本文の challengeToken で渡し、完了のときに本文で返してもらいます。
  • DB には、トークンの SHA-256 だけを保存します。トークンは5分で失効し、1回使うと消えます。
  • Cookie での受け渡しを本文に変えた理由は、下の判断理由に書きます（#230、#232）。
  • RP ID の既定は、本番では mytechpulse.net です（WEBAUTHN_RP_ID）。本番の origin が https であり、localhost でないことを、起動時に検査します。
判断理由（認証まわり）

決めたこと: ログイン試行の制限と、パスワードの強度チェックを必須にする（#186）。

理由:

  • #217 で実装しました。12文字以上にし、よくあるパスワードを拒否します。文字の種類の決まりは設けません。制限はメモリの中で数えます。
選ばなかった案選ばなかった理由
Cloudflare WAF のレート制限だけに任せる利用者名ごとの制限ができない。そのため補助にとどめると、#186 に書かれている。

決めたこと: パスキーには go-webauthn を使う。

理由:

  • #216 で設計しました。
  • 初版は、パスワードと併用します。パスキーだけの利用者は、後で対応します。
  • discoverable と userVerification=required にします。上限は10件です。
  • 実装は4段階で進めました。基盤が #219、登録と設定が #221、ログインが #228、conditional UI が #229 です。
選ばなかった案選ばなかった理由
自前で実装する検証の漏れが起きる危険が大きい。

決めたこと: チャレンジのトークンは、本文の challengeToken で受け渡す（#232）。登録も同じ形にする。

理由:

  • 最初は Cookie で渡していました。複数のタブで開くと Cookie が上書きされ、先に開いたタブのログインが失敗しました（#230）。
  • トークンだけでは何もできず、本人確認つきの署名が必要です。そのため、本文に載せてもできることは増えないと、PR に書かれています。

Cookie で渡し続ける複数のタブで、先に開いたタブが失敗する（#230）。
BroadcastChannel（#229 で検討）複雑さに見合わない。

  • サーバーは Lightsail の東京、1GB です（文書では約 $7/月）。

サーバー側のセッションを使う。すぐに失効できます。XSS で盗まれる範囲が小さくなります。要求のたびに DB を読みます。クロスオリジンなので、CSRF 対策（Origin と専用ヘッダー）が要ります。
興味度を整数（10000 倍）で保存し、計算する。誤差がありません。テストの結果が毎回同じになります。0〜10000 への切り詰め（クリップ）や、整数の割り算の切り捨てに気をつける必要があります。

人の承認なしで、自動でデプロイする。速く反映できます。手作業のミスがありません。検査、自動の戻し、digest での固定に頼っています。
