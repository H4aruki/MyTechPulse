# MyTechPulse Goバックエンド移行設計

- 状態: 承認済み
- 承認日: 2026-09-14
- 親Issue: [#116](https://github.com/H4aruki/MyTechPulse/issues/116)
- 設計Issue: [#117](https://github.com/H4aruki/MyTechPulse/issues/117)

## 1. 背景

MyTechPulseは、QiitaとZennから利用者の興味に合う記事を取得し、優先順位を付けて表示するサービスである。今後は管理者機能、記事の定期収集、AI連携を追加する予定がある。

現行のPythonバックエンドは小規模だが、外部通信と記事変換と推薦計算の集中、API型の手動二重管理、DB変更履歴の欠如、サーバー側で失効できないJWTなどがある。機能と参加者が増えたときの堅牢性・保守性・運用の単純さを改善するため、バックエンドをGo製のモジュラーモノリスへ段階的に置き換える。

## 2. 目標

- 既存利用者、パスワード、タグ、興味度を失わずにGoへ移行する
- 1つのAPIとして簡単に運用しつつ、機能ごとの責務を分離する
- API、DB、外部サービスの境界を型と自動テストで検証する
- GoコードをAPI仕様の正本とし、Swagger UIで閲覧・試行できるようにする
- DB変更、バックアップ、復元、切り替え、切り戻しを再現可能にする
- 新しいメンバーがREADMEと設計資料から開発・検証・運用を理解できるようにする
- 将来の管理者機能、記事定期収集、AIプロバイダー連携を既存機能へ密結合させず追加できるようにする

## 3. 今回行わないこと

- 管理者画面そのものは作らない
- 記事の定期収集や記事保存は実装しない
- AI機能や特定のAIプロバイダー連携は実装しない
- 深層学習モデルを自作しない
- ZennをRSSなど別の取得方式へ変更しない
- 既存利用者データを削除・初期化しない
- Go移行と無関係な画面デザインや機能を変更しない
- Python版を本番切り替え直後に削除しない

## 4. 採用方式

### 4.1 モジュラーモノリス

Go版は1つのAPIバイナリ・1つのコンテナとして配布する。内部は認証、記事、興味プロファイル、推薦、外部メディア連携に分ける。各モジュールは、自分が必要とする小さなインターフェースだけを定義し、HTTPフレームワーク、DBドライバー、外部APIの応答型を業務ロジックへ漏らさない。

依存方向は次のとおりとする。

```text
HTTP入口 → ユースケース → ドメイン型・必要なインターフェース
                              ↑
                  DB・外部APIアダプター
```

共通化は設定、ログ、HTTP安全設定、DB接続など技術的な横断処理に限定する。機能固有の処理を巨大な共通サービスへ集めない。

### 4.2 比較した案

| 案 | 利点 | 欠点 | 判断 |
| --- | --- | --- | --- |
| モジュラーモノリス | 配布が1単位で、機能境界も保てる | 境界をコードレビューで守る必要がある | 採用 |
| 現行PythonレイヤーのGo直訳 | 最初の移植量が少ない | 責務集中と仕様の二重管理が残る | 不採用 |
| 機能ごとのマイクロサービス | 実行時の境界が強い | デプロイ、監視、認証、通信障害の運用が増える | 現在の規模では不採用 |

判断理由は [ADR-0001](../../adr/0001-use-go-modular-monolith.md) に記録する。

## 6. モジュール境界

| モジュール | 責務 | 依存してよいもの | 依存させないもの |
| --- | --- | --- | --- |
| auth | 登録、ログイン、現在利用者、ログアウト、セッション、役割 | 利用者・セッション用DBインターフェース、時計、乱数 | Huma型、pgx型、記事処理 |
| article | 共通の記事表現 | 標準ライブラリ | Qiita・Zennの応答型 |
| interest | タグ興味度、固定小数点変換、クリック更新 | 興味データ用DBインターフェース | HTTP型、外部API型 |
| recommendation | 記事の採点、重複排除、提供元別上位件数 | article、interestの読み取り型 | DBドライバー、HTTPクライアント |
| provider/qiita | Qiitaへの安全な問い合わせと応答検証 | 共通HTTP部品、article | 認証セッション、DB |
| provider/zenn | 現行Zenn APIへの問い合わせと応答検証 | 共通HTTP部品、article | 認証セッション、DB |
| store | 手書きSQL、sqlc生成物、トランザクション | pgx、PostgreSQL | Humaの入出力型 |
| app | 実装を組み立て、HTTP経路を登録する | 全アダプター | 業務ルールそのもの |

将来の定期収集はproviderインターフェースをHTTP画面表示とは別の起動点から再利用する。将来のAI連携は、最初の具体的な用途が決まった時点で、その機能側が必要なインターフェースを定義する。AI用の空モジュールや特定プロバイダー依存は今回作らない。

## 7. APIとSwagger UI

### 7.1 基本方針

- URLは `/api/v1` から始める
- Goコードと型付きハンドラーをAPI仕様の正本とする
- Huma v2からOpenAPI 3.1を生成する
- `server/cmd/openapi` はDBや外部APIへ接続せず仕様ファイルを生成できるようにする
- ローカルと検証環境では `/docs` と `/openapi.json` を提供する
- 本番ではSwagger UI、OpenAPI、JSON Schemaの経路を既定で無効にする
- Swagger UIの標準CDN資産を使う。オフライン閲覧が必要になった場合だけ自己配信を別Issueで検討する
- JSON項目名は既存画面との対応が分かりやすいsnake_caseを維持する
- 成否を本文の `status` 数値では表さず、HTTPステータスと安定した業務エラーコードで表す

### 7.2 最小API

| 方法・パス | 成功 | 主な失敗 | 用途 |
| --- | --- | --- | --- |
| `POST /api/v1/auth/signup` | 201 | 409 利用者名重複、422 入力不正 | 会員登録とCookie発行 |
| `POST /api/v1/auth/login` | 200 | 401 認証失敗、422 入力不正 | ログインとCookie発行 |
| `GET /api/v1/auth/me` | 200 | 401 未認証・期限切れ | 現在利用者の取得 |
| `POST /api/v1/auth/logout` | 204 | なし | 現在のセッション失効とCookie破棄 |
| `GET /api/v1/feed` | 200 | 401 未認証、503 全提供元利用不可 | 推薦フィード取得 |
| `POST /api/v1/feedback/article-clicks` | 204 | 401 未認証、422 入力不正 | 興味プロファイル更新 |
| `GET /health/live` | 200 | なし | プロセス生存確認 |
| `GET /health/ready` | 200 | 503 DB接続不可 | 受付準備確認 |

登録は `username`、`password`、`favorite_tags` を受け取る。usernameは1〜50文字、passwordは1文字以上かつUTF-8で72バイト以内、favorite_tagsは1〜128件、各タグは1〜50文字とする。ログインは `username` と `password` を受け取る。登録・ログインの成功本文は公開可能な利用者情報だけを返し、セッションIDは本文へ入れない。

利用者情報は `id`、`username`、`role` を持つ。roleは今回 `member` と `admin` を定義するが、管理者用APIと画面は作らない。

推薦フィードは次を返す。

```json
{
  "qiita_articles": [],
  "zenn_articles": [],
  "warnings": []
}
```

記事は `title`、`url`、`source`、`tags`、`likes`、`published_at` を持つ。画面が提供元別に表示しているため、移行時は2つの配列を維持する。提供元の一部だけが失敗した場合は200とし、`warnings` に `provider` と安定した `code` を入れる。両提供元が正常に0件を返した場合は200と空配列、両方とも利用不能なら503とする。

クリックは `tags` を1〜50件受け取り、各タグが1〜50文字であることを検証し、大文字小文字を無視して重複を除く。サーバーとフロントはクリック更新を自動再試行しない。受理された各リクエストを1回のクリックとして扱う。

### 7.3 エラー形式

4xxと5xxはRFC 9457 Problem Detailsを基礎とし、`type`、`title`、`status`、`detail`、`instance`、`code` を返す。入力項目ごとのエラーがある場合だけ `errors` を追加する。

- 利用者が対処できるエラーだけ安定した `code` を公開する
- 予期しない内部エラーは同じ一般文言にし、SQL、スタックトレース、外部API本文を返さない
- 利用者不存在とパスワード不一致は、HTTP状態、本文、ログの粒度を同じにする
- リクエストIDはレスポンスヘッダーとログに含め、秘密情報を含めず問い合わせに使えるようにする

## 8. 認証と認可

JWTの `localStorage` 保存を廃止し、十分にランダムな不透明セッションIDをCookieで渡す。DBにはSHA-256ハッシュだけを保存し、平文セッションIDは保存・記録しない。理由は [ADR-0002](../../adr/0002-use-server-side-sessions.md) に記録する。

- セッションIDは暗号学的乱数32バイト以上から生成する
- 本番Cookie名は `__Host-mtp_session` とし、Secure、HttpOnly、SameSite=Lax、Path=/を必須にしてDomainを付けない
- ローカルHTTPでは別名 `mtp_session` を使い、Secureだけを無効にできる設定とする
- セッション有効期限は現行JWTと同じ24時間から開始する
- DBの認証セッションにはハッシュ、利用者ID、作成日時、有効期限を保存する
- 複数端末は別セッションとして共存し、ログアウトは現在のセッションだけを失効する
- ログアウトはセッション行を削除し、セッションが既に無い場合もCookieを破棄して204を返す
- 期限切れセッションは認証に使えない。新しいセッションを作る際に期限切れ行を削除し、清掃失敗だけを理由にログインを失敗させない
- Go版切り替え時に旧JWTは引き継がず、利用者へ一度だけ再ログインしてもらう
- 存在しない利用者でも固定の合成bcryptハッシュを照合し、存在有無による不要な処理差を減らす
- パスワードはUTF-8で72バイト以内か検証し、超過は422とする
- 新しいパスワードハッシュも現行Passlibに合わせbcrypt cost 12で生成する

Cookie認証の更新系APIは、許可Originの検査と `X-MTP-CSRF: 1` ヘッダーの両方を要求する。CORSは許可するOrigin、メソッド、ヘッダーを列挙し、認証付き通信だけ `Access-Control-Allow-Credentials` を有効にする。フロントのfetchは `credentials: include` に統一する。

`user` テーブルへ `role varchar(20) NOT NULL DEFAULT 'member'` と、値を `member` または `admin` に限定するCHECK制約を追加する。既存利用者は全員 `member` とする。認証後の主体は利用者IDとroleを持ち、将来の管理者APIはサーバー側でroleを検査する。今回、管理者への昇格操作や管理者APIは提供しない。

## 9. DB変更とデータ保全

### 9.1 既存データ

既存の `user`、`tag`、`recommend` と、引用符が必要な `user_ID`、`tag_ID` を切り戻し期間中は改名しない。Goコードでは `UserID`、`TagID` として扱う。

`recommend` は推薦結果ではなく、利用者と技術タグの組み合わせごとの興味度を保存している。計算上は0〜1、保存時は10000倍した整数である。既存値は移行前後で一致させる。

### 9.2 マイグレーション

gooseのSQLマイグレーションを正本とし、API起動時には自動適用しない。`server/cmd/migrate` をCIまたは明示的な運用手順から単発実行する。

最初のベースラインは次の2経路を同じファイルで扱う。

1. 空DBでは既存3テーブルと制約を作る
2. 既存DBではテーブルを作り直さず、列型、NULL、主キー、外部キー、UNIQUE、CASCADEを検証し、不一致なら失敗する

`CREATE TABLE IF NOT EXISTS` だけで互換と判定しない。検証成功後にだけgooseの適用済み版として記録する。

次の変更として、既定値 `member` を持つrole列と、認証セッションテーブル `auth_session` を追加する。`auth_session` はSHA-256ハッシュを格納する主キー、`user.user_ID` へのCASCADE付き外部キー、作成日時、有効期限を持ち、利用者IDと有効期限に索引を付ける。どちらも現行Python版が無視できる追加変更とし、切り戻し期間中に既存列の削除・改名・型変更は行わない。本番の切り戻しにdownマイグレーションは使わない。

### 9.3 タグと興味度

- 既存タグの表記とIDを書き換えない
- 新規登録で選択したタグの `recommend.match_int` は現行どおり初期値1とする
- 比較用の正規形は前後空白を除いた小文字とし、画面表示は既存表記を維持する
- 大文字小文字だけが異なる既存タグを #119 で検査する
- 衝突が見つかった場合は自動統合せず、対象データと影響を示して別途許可を得る
- クリック更新は利用者単位でDBロックを取り、同時更新による取りこぼしを防ぐ
- 重み計算は固定小数点整数で行い、減衰は8/10、クリックタグへの加算は2000とする。既存の保存値は書き換えない
- 現行Pythonの浮動小数計算と比較すると、保存範囲0〜10000のうち減衰26値・クリック加算83値で結果が1だけ小さくなる丸め誤差がある。Go版は正確な整数式を採用し、影響値では次回クリック時に最大1だけ大きくなることを意図的な修正として #118 と #123 のテストへ記録する

### 9.4 バックアップと復元

- 変更直前にPostgreSQLカスタム形式の完全バックアップを取得する
- SHA-256チェックサム、取得日時、対象DB、スキーマ版を秘密情報なしで記録する
- 新しい空DBへ実際に復元し、件数、関連、制約、シーケンスを検査する
- 合成利用者と合成タグを作成し、復元後の連番IDが衝突しないことを確認する
- DBロール、環境変数、Dockerボリューム、Caddy設定などバックアップ外の要素を手順で再現する
- 本番データをリポジトリ、CI、Issue、通常ログへ入れない
- 本番サーバーとは別の暗号化保存先、費用、保存期間、世代削除は #119 で案を提示し、承認後に有効化する

## 10. 記事取得と推薦

### 10.1 外部メディア

QiitaとZennは別アダプターとし、外部応答型を各アダプターの外へ出さない。接続先ホストを固定し、想定外ホストへのリダイレクトを拒否する。QiitaのAuthorizationヘッダーを別ホストへ転送しない。

- Qiita: `https://qiita.com/api/v2/tags/{tag}/items`
- Zenn: 現行の `https://zenn.dev/api/articles`
- Zennの `topicname` は小文字化し、`count=5` を維持する
- Zennの `liked_count` は表示用に維持する
- URLへ入れるタグはパス要素またはクエリ値として安全にエンコードする
- 外部応答は1リクエスト2MiBを上限とし、接続を含む1回のタイムアウトを5秒、推薦フィード全体の外部取得期限を8秒とする。値は起動時検証済み設定でより小さくできる
- GETの一時的な通信障害と502・503・504だけ、リクエスト期限内で最大1回再試行できる
- 429とその他4xxは自動再試行せず、Retry-Afterと残りリクエスト数を秘密情報なしで記録する
- 一方の提供元が失敗しても他方を返し、提供元別の警告を付ける

Zennは公式仕様を確認できない現行APIを継続使用する。固定レスポンスによる契約テストで必須項目の欠落と型変更を検出し、変更時はZennだけを部分失敗にする。RSSなどへ自動で切り替えない。

### 10.2 現行の絞り込みと採点

正式なAPI詳細資料と現行コードに合わせ、次を互換対象とする。

- 興味度上位5タグでQiitaとZennを並行取得する
- Qiitaは直近5日以内、Zennは直近2週間以内を候補にする
- Qiitaは記事タグと興味タグを小文字で比較する
- Zennは検索に使ったトピックを記事タグとして補い、複数検索で同じURLが出たらタグを統合する
- URL単位で重複を除く
- Qiitaのスコアは「一致したタグ興味度の合計 ×（likes + 1）」とする
- Zennは提供元側の並び順を利用するため「一致したタグ興味度の合計」だけで採点する
- Zennが期間条件で0件になった場合、追加通信せず取得済み結果から期間条件だけを外す
- 提供元ごとに上位10件を返す

`AGENTS.md` と `mytechpulse-domain` Skillの短い要約には、両提供元を5日・同じ計算式と読める記述がある。これは現行コードおよび `docs/BasicDesignSpecifications/API/Details/News.md` と一致しない。#118で上記挙動を特性テストに固定し、#129で要約側も一致させる。

## 11. 設定、ログ、終了処理

設定は環境変数から読み、必須値、URL、時間、サイズ上限、Cookie安全属性を起動前に検証する。`.env` の値は読み取らず、項目と説明は `.env.example` を正本にする。本番の秘密情報に開発用既定値を設けない。

JSON構造化ログを標準出力へ出す。時刻、レベル、処理名、リクエストID、HTTP状態、所要時間、提供元、結果コードを記録できるようにする。パスワード、Cookie、平文・ハッシュ済みセッションID、DB接続文字列、Qiitaトークン、外部APIの未検証本文は記録しない。

HTTPサーバー、DB問い合わせ、外部APIに個別のタイムアウトを設け、リクエストのキャンセルを下位処理へ伝える。終了通知を受けたら新規受付を止め、処理中リクエストへ猶予を与え、DB接続を閉じて終了する。

## 12. OpenAPIとフロントエンド

`server/cmd/openapi` が `server/openapi/openapi.json` を生成し、`openapi-typescript` がフロント用の生成型を作る。生成型と手書きのAPIクライアント・画面ロジックを別ファイルにする。

CIではOpenAPIとTypeScript型を再生成し、コミット済み生成物に差分が出たら失敗させる。これにより、バックエンドの型、OpenAPI、フロント型の手動三重管理を防ぐ。

フロントは次を変更する。

- APIパスを `/api/v1` へ変更する
- Bearerトークンと `localStorage` の認証保存を削除し、Cookie送信へ切り替える
- 更新系へCSRF用ヘッダーを付ける
- 本文 `status` の分岐をHTTP状態とProblem Detailsの `code` へ置き換える
- ログアウト時にサーバーAPIを呼び、その後ローカルの認証状態を消す
- 未認証、入力不正、重複、通信障害、全提供元障害を区別して表示する
- 一方の提供元だけが失敗した場合、取得できた記事を表示しつつ控えめな警告を表示する
- 既存のLPと主要画面の見た目は意図せず変更しない

## 13. テスト戦略

### 13.1 移行前の特性テスト

#118でPython版に一時的な特性テストを追加し、次を固定する。

- 会員登録、ログイン、認証失敗の現行応答
- Passlibが生成する合成bcrypt `$2b$` ハッシュ
- 興味度の10000倍整数、減衰、加算、丸め境界
- QiitaとZennの期間、タグ照合、重複排除、採点、上位件数
- Zennの期間フォールバック
- 外部通信を行わない固定Qiita・Zenn応答

意図した新APIとの差は「維持する仕様」と「意図的に変更する旧契約」に分ける。独自 `status`、JWTの本文返却、旧パスはデータ互換ではなく意図的な変更として記録する。

### 13.2 Go版の自動テスト

- interestとrecommendation: テーブル駆動の単体テスト、境界値、重複タグ、大小文字、0件
- auth: 登録、ログイン、同一失敗応答、Cookie属性、期限切れ、失効、複数端末、CSRF、CORS
- provider: 固定HTTPサーバーを使った応答検証、タイムアウト、サイズ超過、リダイレクト、429、部分失敗
- store: PostgreSQL 17を使ったSQL結合テスト、制約違反、トランザクション失敗、同時クリック
- handler: HTTP状態、Problem Details、OpenAPIへ定義された入出力
- frontend: 生成型の型検査、既存Vitestによる認証・エラー・主要画面分岐
- migration: 空DBと既存スキーマ相当DBの両方への適用、再実行時の状態確認

ブラウザからの登録、ログイン、記事一覧、クリック、ログアウト、切り戻しは #126 の検証環境で通し確認する。新しいブラウザE2Eライブラリは今回の承認対象に含めず、必要になった場合は名称・理由・影響を説明して別途許可を得る。

## 14. CI、成果物、公開

- Goの整形、`go vet`、単体・結合テスト、ビルドを実行する
- フロントのlint、テスト、型チェックを含むビルドを維持する
- DBマイグレーションを空DBと既存相当DBで検査する
- OpenAPIとフロント生成型の差分を検査する
- GoコンテナはCIで一度だけ作り、同じコミットSHAとダイジェストをリハーサル・本番・切り戻しで使う
- 本番サーバー上でソースから再ビルドしない
- DBマイグレーションはAPI起動と分け、成功した場合だけ公開先を切り替える
- GitHub Actionsの権限を最小化し、同時デプロイを防ぎ、可能なActions参照を完全なコミットSHAへ固定する
- Go版切り替えまでは、main更新でGo版を本番へ自動反映しない

GHCRは非公開を初期案とする。パッケージ保存を初める前に、公開範囲、取得認証、保持期間、費用への影響を提示して別途承認を得る。Codexは本番サーバーへ直接接続せず、公開は承認済みCIだけで行う。

## 15. 切り替えと切り戻し

切り替えは5〜30分のメンテナンス作業として行う。#126で本番相当データによる全手順をリハーサルし、30分以内に終わる見込みと中止条件を確認してから #127へ進む。

1. 利用者向け案内と作業者、開始・中止条件を確認する
2. 書き込みを止め、メンテナンス応答へ切り替える
3. 最終バックアップ、チェックサム、件数を確認する
4. リハーサル済みの追加マイグレーションを適用する
5. 固定ダイジェストのGo APIを起動し、ready確認を行う
6. Go版に対応するフロントを公開し、登録からログアウトまで確認する
7. 利用者、タグ、興味度、関連件数を照合する
8. 中止条件が無ければメンテナンスを解除し、監視期間へ移る

切り戻し単位はAPIだけではなく、互換するフロントとの組み合わせとする。Python APIイメージ、旧フロント成果物、Go版適用前の識別子を保持する。Go版が追加したrole列と認証セッションテーブルはPython版が無視できるため、利用者データを巻き戻さず旧アプリへ戻す。本番切り戻しで破壊的なdownマイグレーションを実行しない。

## 16. 採用する技術

| 技術 | 役割 | 採用理由 | 主な影響 |
| --- | --- | --- | --- |
| Go 1.26系 | API実装 | 静的型、単一バイナリ、標準HTTP機能 | Pythonとは別のビルド手順が増える |
| Huma v2 | 型付きHTTP、入力検証、OpenAPI 3.1、Swagger UI | コードとAPI仕様を同じ型から生成できる | Humaの登録方式に合わせる必要がある |
| pgx v5 | PostgreSQL接続 | Go向けの直接的なPostgreSQL機能と接続プール | SQLAlchemyはGo版で使わない |
| sqlc | SQLからGo型を生成 | SQLを見える形で保ち、結果を型検査できる | 生成手順と生成物管理が必要 |
| goose | SQLマイグレーション | 適用順と履歴を明示できる | 起動とは別の運用手順が必要 |
| x/crypto/bcrypt | パスワード照合 | 既存Passlib bcryptとの互換を保てる | 72バイト上限を入力検証へ反映する |
| openapi-typescript | フロント型生成 | 手作業のAPI型同期をなくす | frontendの開発用依存と生成コマンドが増える |

Go標準の `net/http`、`log/slog`、`crypto/rand`、`crypto/sha256` を優先し、追加ルーター、ORM、DIコンテナ、汎用リトライライブラリは導入しない。Go、CI、Dockerは同じminor版を使い、patch更新は通常PRで検証する。
