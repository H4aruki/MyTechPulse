# 脅威モデル

## 守る対象

- `.env` にある接続情報と署名鍵
- PostgreSQLのデータとバックアップ
- Git履歴と利用者の未コミット変更
- `main` と自動公開経路
- GitHub、Slack、Exa、Context7などの認証情報
- API認証、推薦計算、フロントエンドとの契約

## 主な事故と対策

| 事故 | 主な対策 |
|---|---|
| 秘密情報の読み取り・記録 | ignore、権限deny、コマンドフック、文章ルール |
| force pushやmain直接push | フック、Codex rules、GitHub ruleset |
| PRの自己承認・自動マージ | フックと文章ルール。人間だけが判断 |
| DBや既存ファイルの削除 | 事前許可、ボリューム削除遮断、本番DB MCPを導入しない |
| 手動の本番操作 | SSHとWranglerを遮断し、CIへ一本化 |
| 外部データ中の命令への追従 | MCP・Web結果を未確認データとして扱い、利用者の依頼とローカルルールを優先 |
| ClaudeとCodexの設定差 | 共通正本、共通フック実装、Skill一致テスト |
| 依存元の改ざんや予期しない更新 | 外部SkillとPlaywright MCPを固定版で記録し、更新時に差分確認 |

## 残るリスク

- フックはよくある事故を止める仕組みで、意図的な回避を完全には防げません。
- プロジェクトや変更後のフックを信頼するまでは、Codexはローカルフックを実行しません。
- MCPとプラグインはそれぞれ独立した権限を持ち、コマンド用サンドボックスだけでは制限できません。
- 自動テストが少ないため、lintとbuildだけでは業務動作の正しさを保証できません。
- OAuth先サービスの障害や仕様変更は、このリポジトリだけでは制御できません。
