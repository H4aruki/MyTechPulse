01プロダクト一言

Qiita と Zenn から、利用者の興味タグに合う新しい技術記事を集めて並べる、パーソナライズ技術ニュースWebアプリ。

  • 登録時に興味タグを選ぶ → 記事一覧を開くたびに、興味の強い上位5タグで Qiita・Zenn をその場で検索 → 点数順に提供元ごと最大10件表示。
  • 記事をクリックすると、その記事のタグの興味が強まり、他のタグは少し弱まる（直近の関心に寄る）。
  • 公開URL: https://mytechpulse.net（画面）／ API は api.mytechpulse.net。
  • ログイン後の画面: 記事一覧 /app/articles、マイページ /app/mypage（#238、利用者名の表示と設定へのリンク）、設定 /app/settings（パスキー管理）。
  • 記事を開いた利用者向けのアンケート（利用者フィードバック、/api/v1/user-feedback/*）も動いている。
出典: README.md、AGENTS.md「プロジェクト概要」、frontend/src/App.tsx、docs/BasicDesignSpecifications/FeaturesList.md F-7-2、server/internal/userfeedback/

05おすすめの流れ（GET /api/v1/feed 1リクエストごと）

  1. 本人確認: セッションCookie → auth.Authenticate。失敗は 401。
  2. 興味度を読む: その利用者の recommend 全行を取得。正規化後に同名タグがあればエラー（500）。
  3. 上位5タグ: 値の降順、同値は正規化タグ名の昇順で並べて先頭5件。
  4. 並列取得: 5タグ × {Qiita, Zenn} ＝ 最大10個の goroutine。結果はバッファ付き channel で全件回収（errgroup は使っていない）。全体の期限 FEED_TIMEOUT 既定 8秒、外部1回あたり PROVIDER_TIMEOUT 既定 5秒。
    Qiita: /api/v2/tags/{tag}/items?page=1&per_page=20（Bearer トークン）／ Zenn: /api/articles?topicname={tag}&count=5
  5. 検証と期間の絞り込み: 記事ごとに検証。Qiita は直近5日以内のみ。Zenn は直近14日以内を採用し、0件のときだけ古い記事で補う（追加の問い合わせはしない）。Zenn 記事には検索に使ったタグを記事タグとして足す。
  6. 重複除去: URL 単位でまとめ、タグは和集合。
  7. 採点（§6 の式）→ 点数降順、同点は公開日時が新しい順 → 提供元 → URL。
  8. マージして返す: qiita_articles（最大10）・zenn_articles（最大10）・warnings。片方の提供元だけ失敗 → 成功側を返し warnings に provider_unavailable。両方失敗 → 503。

採点式

興味合計 = Σ（記事タグのうち、利用者が recommend に持つタグの match_int）
　※ 合計に使うのは上位5タグだけでなく、利用者が持つ全タグの重み
Qiita の点数 = 興味合計 × (likes + 1)
Zenn の点数　= 興味合計（いいね数は掛けない）

Zenn に反響を掛けない理由は README に「取得時点で提供元のトレンド順に絞り込まれているため重ねて数えない」とある。コード上の Zenn 呼び出しは topicname と count だけで、並び順の指定パラメータは無い（Zenn 側の既定の並び順は未確認）。

06興味学習の式（固定小数点）

Scale = 10000（1.0）　　DecayNumerator/DecayDenominator = 8/10　　ClickBoost = 2000（0.2）

【会員登録時（#203、main）】選んだタグ = 10000（1.0）／ tag 表にある選ばなかった全タグ = 8000（0.8）
　→ 利用者作成・興味度・セッションを 1トランザクションで作成

【記事クリック時 POST /api/v1/feedback/article-clicks】
　① 全タグ: v ← clamp(v) × 8 / 10　（整数演算）
　② クリックした記事のタグ（正規化・重複除去）: v ← min(v + 2000, 10000)
　③ 未所持のタグ: 2000 で新規作成（tag 表に無ければ tag も作成）

計算例

React（選択）100008000
Docker（未選択）80008000×0.8＋2000 = 8400
その他の未選択80006400
  • 同じ利用者のクリック更新は SELECT … FOR UPDATE（利用者行ロック）付きトランザクションで直列化。
  • 入力はタグ1〜50件・各1〜50文字。学習の送信が失敗しても画面にエラーは出さない（閲覧を妨げない）。
  • 浮動小数点を使わないのは、小数のまま保存すると誤差が出るため（DB文書の説明）。
事実として言える副作用: 選んだタグが5個未満だと、上位5の残りは 8000 同士の同点になり、正規化タグ名の昇順で埋まる。これを変える提案が未マージの PR #242（§12）。

07認証

セッション（ADR 0002）

  • ログイン/登録成功で 32バイト乱数トークンを発行 → Cookie で渡し、DB には SHA-256 だけ保存。既定有効期限 24時間（SESSION_TTL）。
  • Cookie: 本番 __Host-mtp_session（HttpOnly・Secure・SameSite=Lax・Path=/）、開発 mtp_session。
  • ログアウトでその端末のセッション行だけ削除（他端末は残る）。期限切れの掃除はログインのたびに実行。
  • CSRF: /api/v1/ の更新系は「許可 Origin」かつ「X-MTP-CSRF: 1 ヘッダー」が必須。CORS も許可サイト限定。
  • 旧 Python 版の JWT（localStorage）は引き継がず、切替時に一度だけ再ログイン。

パスワード

  • bcrypt コスト 12（旧 Python/Passlib と同じ。既存の $2b$ ハッシュをそのまま検証）。72バイト上限。
  • 存在しない利用者でもダミーハッシュと照合し、応答は区別しない（どちらも invalid_credentials / 401）。
  • 新規パスワード: 12文字以上・利用者名と同一不可・よく使われるパスワード一覧に含まれないこと（文字種ルールなし、NIST SP 800-63B）。ログイン照合には適用しない。（#217）
  • ログイン試行制限（プロセス内メモリ、#217）: 利用者名ごと15分に5回失敗で 1→2→4…分の締め出し（最大15分）、IPごと15分に20回失敗で締め出し、パスキーのログイン開始は IP ごと15分に60回まで。IP は CF-Connecting-IP。本番で CLIENT_IP_HEADER が空なら起動しない（#231）。

パスキー（WebAuthn）

  • 登録・一覧・名前変更・削除（設定画面、#221）／ログイン（#228）／自動入力 conditional UI（#229）。
  • ログインは利用者名なしで選ばせる（allowCredentials 空）。
  • チャレンジ: 使い捨てトークンをレスポンス本文の challengeToken で渡し、完了時に本文で返す。DB には SHA-256 のみ、5分で失効、1回で消費。Cookie 受け渡しから本文へ変えたのは、複数タブで先に開いたタブのログインが失敗する問題のため（#230 → #232）。
  • RP ID は本番 mytechpulse.net が既定（WEBAUTHN_RP_ID）。本番の origin は https・localhost 不可を起動時に検査。

08インフラ・デプロイ・CI

本番の置き方

  • Lightsail 東京 1GB（文書上 約$7/月）。メモリ対策にスワップ 2GB・vm.swappiness=10。
  • Docker Compose: db（postgres:17-alpine、127.0.0.1:5432 のみ）、api-go（127.0.0.1:8001 のみ）、caddy（80/443、443/udp）。外部へは Caddy だけが開く。

自動デプロイ（人の承認なし。GO_DEPLOY_ENABLED=true のときだけ）

  1. 配布物（API イメージ・画面・運用ファイル・manifest）を一度だけ作り、digest で固定。
  2. SHA-256 照合 → サーバーへ送る → ops/deploy_go.sh: ロック → 入力確認 → 現行版を記録（戻し先）→ 新イメージ取得 → DBバックアップ → 移行（追加のみ・入れ替えより先） → 入れ替え → 疎通確認。
  3. 疎通失敗なら確認なしで直前のイメージへ自動ロールバック（DB は戻さない）。
  4. API 成功時だけ Cloudflare Pages へ画面を公開（画面は新 API 前提のため）。サーバー上でソースからビルドはしない。

09設計上の制約・トレードオフ

決めたこと得たもの払っているコスト（事実）
記事を DB に持たず、毎リクエスト外部 API を呼ぶ実装が単純、常に新しい記事、記事データの保守不要表示ごとに最大10回の外部呼び出し。外部の遅延・障害・レート制限の影響を直接受ける（8秒で打ち切り、片側失敗は warnings）。日次一括化は未実装（#66）
Lightsail 1GB に API・DB・Caddy を同居月約$8、DB往復が速い、構成が単純単一障害点（サーバー停止＝全停止、要件上許容）。メモリが小さくスワップ前提
移行は追加のみAPI だけ旧版へ自動ロールバックしても DB 互換が保たれる列の削除・改名・型変更ができず、古い列が残る
ログイン試行制限をプロセス内メモリで持つ追加インフラ不要再起動で数え直し。API が1台である前提
サーバー側セッション即時失効・XSSで盗まれる範囲の縮小毎リクエスト DB 参照、クロスオリジンなので CSRF 対策（Origin＋専用ヘッダー）が必要
興味度を整数（×10000）で保存・計算誤差なし・決定的なテストクリップ（0〜10000）や整数除算の切り捨てを意識する必要
未選択タグも 0.8 で全行作成（#203）選んだタグが少なくても上位5が埋まる同点の未選択タグは名前順で選ばれる（意図との差は #242 で議論中）。利用者×全タグ分の行
人の承認なしの自動デプロイ速く反映、手作業ミスなし検査・自動ロールバック・digest 固定に依存

深掘りされたときの想定問答（事実ベース）

Q. なぜ記事を保存しない？
テーブル3つ・書き込みも少ない小規模で始め、常に新しい記事を出すため都度取得にしている。外部APIの上限とダウン時の表示が課題で、日次一括化は #66 で検討中（未実装）。
Q. 外部APIが落ちたら？
片方だけなら成功側を返し warnings で通知。両方失敗で 503。全体8秒・1回5秒で打ち切り。
Q. なぜ整数で持つ？
小数のまま保存すると誤差が出るため、×10000 の固定小数点で保存・計算。
Q. なぜ 0.8 / 0.2？
文書に定数値の決定理由なし 「全体を弱めてクリックしたタグを強める＝直近の関心に寄せる」という目的のみ記載。
Q. DBを変えて失敗したら？
移行は追加のみで、API だけ直前の版へ自動で戻す。DB は巻き戻さない設計。
