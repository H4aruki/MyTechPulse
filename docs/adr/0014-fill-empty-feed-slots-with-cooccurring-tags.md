# おすすめの空き枠を、興味のあるタグと同じ記事によく付くタグ（共起）の記事で埋める

- 状態: 提案。PR がマージされたら採用にする。共起回数の下限（3）は仮の値で、未確定
- 日付: 2026-11-13（起案）
- 決定者: K.Haruki（マージで決定）。起案は AI（Rex。実装は Grok、親の確認は Rex）

## 背景と問題

- おすすめ記事は、利用者の興味度が高い上位5タグから取る。#240（PR #242）で「選ばなかったタグの興味度は0（行を作らない）」にしたため、登録直後など興味のあるタグが5つに満たない利用者は、記事を取る枠が空く。
- いまは空いた枠を人気の記事（いいね数の多い記事）で埋めている。人気の記事は利用者の興味と関係なく選ばれるので、好みに合わない記事が混ざる。
- Issue #241 は、興味のあるタグに「似たタグ」の記事で空きを埋める提案。似ている度合いの求め方を決める必要があった。
- #66 で記事とタグを DB（`articles`、`article_tags`）に貯めるようになり、外部 API を呼ばずにタグ同士の関係を数えられるようになった。

## 検討した案

| 案 | 内容 | 採否 | 採らなかった理由（採用なら採った理由） |
|---|---|---|---|
| 共起の回数（Issue の案 B） | `article_tags` で、興味のあるタグが付いた記事に一緒に付いている別のタグを、記事の数が多い順に使う | 採用 | 外部サービスも新しい依存も要らず、SQL 1本で求まる。Issue の第一案 |
| タグ名の埋め込み（案 A） | タグ名を埋め込みモデルでベクトルにし、近いものを似たタグとする | 不採用 | 外部の埋め込み API は有料になりうる（オーナーの許可が要る）。サーバー内でモデルを動かすと 1GB の本番には重い。`pgvector` などの導入も要る |
| 利用者の興味度から求める（案 C） | 同じ人が一緒に興味を持つタグほど似ているとみなす | 不採用 | 利用者が少ないうちは精度が出ない。他の利用者の興味を使うことになり、説明も要る |
| 割合で測る（Jaccard 係数など） | 一緒に付いた記事の数を、それぞれのタグの記事数で割る | 不採用 | Issue の文面は回数で、割合の式を選ぶ裏づけが無い。よく付くタグが勝ちやすい弱さは残る（下の「結果と代償」） |
| 点数で混ぜて並べる | 興味タグ・似たタグ・人気の記事を同じ点数で並べ替える | 不採用 | 似たタグと人気の記事は興味度の点数がたいてい0なので、混ぜるといいねの多い人気の記事が前に出て、似たタグを入れた意味が薄れる |
| 興味タグが5つあっても、記事が10件に足りなければ似たタグで埋める | 空きの判定を記事数で行う | 不採用 | Issue の空きは「上位5タグが埋まらないとき」。5つあるときの不足は、これまでどおり人気の記事で埋める |
| 即時検索（開発・試験用の経路）でも似たタグを使う | 外部 API を毎回呼ぶ経路にも入れる | 不採用 | 共起の材料は DB の `article_tags` にあり、即時検索の経路には無い。本番は DB から読む経路なので効果は変わらない |
| 新しい索引とマイグレーション | 共起の集計用の索引を足す | 不採用 | 記事は数千件の規模で、既存の索引（`("tag_ID", published_at)` と主キー `(article_id, "tag_ID")`）で引ける |

## 決定

- 本番の DB から読むフィード（`ARTICLE_FETCH_ENABLED` が有効なとき）だけで、次の順に並べる: 興味のあるタグの記事 → 似たタグの記事 → 人気の記事。
- 似たタグを探すのは、興味のあるタグが5つ未満で、その提供元の記事が10件に満たないときだけ。集計はフィード1回につき SQL 1本（`ListCooccurringTags`）。
- 似たタグの数は「5 − 記事探しに使った興味タグの数」まで。共起回数が3未満のタグ（`minCooccurrence`）と、興味度が0より大きいタグは使わない。同じ回数ならタグ名の順。
- 数える範囲は、`article_tags` に残っている記事すべて（保持期間を過ぎた未保存の記事は定期取得が消している）。似たタグの記事を出す期間は人気の記事と同じ（Qiita 5日、Zenn 14日）。
- API の形、DB のスキーマ、画面の文言は変えない。

## 理由（判断基準）

1. 費用と依存を増やさない（外部の有料 API、新しいライブラリ、マイグレーションを使わない）。
2. 今の動きを壊さない（興味タグの記事が先、足りない分は人気の記事、という既存の約束を保つ）。
3. 本番（メモリ 1GB）で重くしない（集計はフィード1回に1本、空きがあるときだけ）。
4. 裏づけの無い数値を増やさない（割合の式や重みは入れず、下限だけを仮の値として明記する）。

## 根拠のデータ・事実

- 2026-10-22 の本番の初回取得で、Qiita 112 ページ、Zenn 100 トピックを取り、`articles` は 2200 行（Issue #66 のコメント）。記事は数千件の規模。
- Zenn の API は記事のトピックを返さないため、Zenn の記事には検索したトピックのタグが1つ付くだけ。共起の多くは Qiita の記事から出る（Issue #241、#66 のコメント）。
- 共起回数の分布は本番で測っていない。下限3は、1回（その記事だけの偶然）と2回（短い連載でも起きる）を外すための仮の値。
- 確認（2026-11-13、box）: `gofmt`、`go vet ./...`、`go test ./internal/recommendation/ ./internal/store/` が成功。DB 結合試験は box に DB が無いため CI で確かめる。`go run ./cmd/openapi` の後も `openapi.json` に差分なし。

## 結果と代償

- 良くなること: 興味のあるタグが少ない利用者にも、好みに近い記事が人気の記事より先に出る。費用・依存・スキーマの変更なし。
- 代償: 回数で測るので、多くの記事に付く一般的なタグ（例: 言語名）が選ばれやすい。Zenn の記事は共起が出にくい。
- 残るリスク: 下限3が本番の分布に合わず、似たタグがほぼ出ない、または関係の薄いタグが出る。対策: 下限は Go の定数1か所だけで変えられ、SQL は回数をそのまま返す。似たタグが0件なら、これまでどおり人気の記事で埋まる。
- プライバシー: 新しい個人情報は取らず、他の利用者の興味も使わない。#298 のプライバシーポリシーの文面（興味タグと興味度を記事の選択と並べ替えに使う）の範囲内。

## 見直し方

- マージから2週間後（目安 2026-11-27）に、本番の `article_tags` で共起回数の分布（回数ごとのタグの組の数）を数え、下限3が妥当かを Rex が報告し、K.Haruki が決める。
- 見直しのきっかけ: 「関係の薄い記事が出る」という声、または似たタグがほとんど出ないことが分かったとき。割合（Jaccard など）や案 A（埋め込み）への切り替えは、そのときに新しい ADR で決める。
