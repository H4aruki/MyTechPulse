# 1日の上限は設けず、大きさの上限を毎週見直す

- 状態: 採用（2026-11-13）。数字は初期値で、毎週見直す
- 日付: 2026-11-13
- 決定者: Haruki。AIは起案者
- 全体の概要: [0004](0004-automerge-small-prs-by-deterministic-script.md)

## 背景と問題

自動マージの歯止めを、何で掛けるかを決める必要があった。初期案は「1日3本まで」だった。一方で、パスだけで決めると、許可パスの中の大きな機能追加も通ってしまう。そこで、本数の上限と、1本の大きさの上限をどうするかを決めた。

## 検討した案

| 案 | 内容 | 採否 | 採らなかった理由（採用なら採った理由） |
|---|---|---|---|
| A | 1日の本数の上限は設けない | 採用 | 3本では足りない（Harukiさん）。歯止めはサイズとパスに任せる |
| B | 1日3本まで（初期案） | 不採用 | Harukiさんが「足りない。無限に」と指定した |
| C | 大きさの制限なし | 不採用 | 場所だけだと「中身は大きな機能追加」が通る |
| D | 200行から始める（ゆるめ） | 不採用 | 最初の方針（60行・4ファイル・300行）のままでよいと、Harukiさんが決めた |
| E | 初期値は60行・4ファイル・300行。毎週見直す（採用） | 採用 | 行数が最も簡単な目安。テストは多めに許す |
| F | 見直しは2週間ごと | 不採用 | Harukiさんが「毎週」にした |

## 決定

- 1日の本数の上限は**なし**。
- 大きさの初期値: テスト以外の変更行（追加＋削除）60行以下、テスト以外の変更ファイル4つ以下、全体の変更行300行以下。
- 数字は**毎週**見直す。本番で自動マージが動き出してから、毎週1回、次を表にして提案する。ルールを変えるPRは人がマージする。
  - 自動マージした本数と、戻した本数
  - クラスB・Cに回った理由の内訳（行数、パス、テスト、判断事項）
  - 60行・4ファイル・300行を、緩めるか締めるかの提案
  - 分割して入った変更が無いか（近いパス・近いIssueの連続）

## 本人の発言

- 2026-11-13 午後（時刻の記録なし）:「それから自動マージは1日3回では足りない。無限にやれるようにするべき。」
- 2026-11-13（時刻の記録なし）:「大きさは制限する必要があるの？」。Rex が理由を説明したあとに:「初期サイズは最初の方針のままでいいけど、定期的に見直しはしたい」
- 2026-11-13（時刻の記録なし）: Rex が「2週間ごとでいい？」と聞いたのに対して:「毎週」

## 理由（判断基準）

1. 本数ではなく、1本ごとの中身（パスと大きさ）で安全を決めること。
2. 大きさは、場所だけでは防げない「大きな機能追加」を止める最も簡単な目安であること。
3. 数字は最初の勘なので、実際のPRで確かめて直せること（毎週）。

## 根拠のデータ・事実

- 過去のマージ済みPR 40本の判定（2026-11-13 16:13 JST、コミット 5761519）で、大きさのルールに当たった数は、size.nonTestLines 19、size.nonTestFiles 11、size.totalLines 9だった。
- 設計書の記録では、直近の小さい修正は数十行で、#272 は194行のため対象外になる程度だった。
- 小さく分けて大きい変更を入れる抜け道は、日次上限ではなく、サイズとパスを第一の歯止めにし、週次見直しで分割の傾向を見て防ぐ。

## 結果と代償

- 良くなること: 1日に何本でも、条件を満たせば自動でマージされる。
- 代償: 本数で止まらないので、分割して入った変更が通る可能性がある。60行の制限が厳しすぎれば、人に回るPRが多くなる。
- 残るリスク: 週次の見直しをしないと、数字が実態とずれる。
