# Goのimportは、mainのgo.modにある依存を許す

- 状態: 採用（2026-11-13 17:04 JST に Harukiさんが了承）。実装は [PR #303](https://github.com/H4aruki/MyTechPulse/pull/303) に含まれ、マージ済み（2026-11-13 16:51 JST、f4125a2）

- 変更する決定: [0005](0005-eligibility-decided-by-deterministic-script.md) のGoのimportに関する部分

## 背景と問題

設計書の元のルールは、Goの外部 import を「自リポジトリと標準ライブラリだけ」に限るものだった。新しい依存を持ち込むPRを自動マージの対象から外すための線引きである。

この線引きで過去40本のPRを試したところ、1回目（コミット 050fd23）で、`import.go` の規則に7本が当たった。#272、#288 などである。すでに `go.mod` にある依存（pgx、goose など）をテストで使うだけでも、外部 import として対象外になっていた。守りたいのは「新しい依存を入れること」であり、「すでに使っている依存を使うこと」までは止めたくない。

## 検討した案

| 案 | 内容 | 採否 | 理由 |
|---|---|---|---|
| A | 元のまま「標準と自リポジトリだけ」 | 不採用 | 1回目の試しで7本が `import.go` で落ちた。すでにある依存の利用まで止めてしまう |
| B | main の `go.mod` にあるモジュールの import は許す（TypeScript で `package.json` にあるものを許すのと同じ考え方） | 採用 | 新しい依存は `go.mod` と lockfile を触るので、除外パスの規則で別に止められる。既存依存の利用だけを通せる |
| C | import の検査をやめて、lockfile の検査だけに任せる | 不採用 | 依存の足し方が `go.mod` を触らない形（取り込み方の例外など）で漏れたときに、止める層が無くなる。Bなら二重に守れる |

## 決定

案Bにする。判定スクリプトは、base（main）の `go.mod` を取得し、そこにあるモジュールの import は許す。`go.mod` に無いモジュールの import は、これまでどおり対象外にする。

## 理由（判断基準）

- 止めたいもの（新しい依存の持ち込み）だけを止め、すでにある依存の利用は通す。
- 案Bは、除外パスの規則（`go.mod`・lockfile）と合わせて二重に守る。
- 機械で決められること（`go.mod` に載っているか）は、決定的なスクリプトで決める（[0005](0005-eligibility-decided-by-deterministic-script.md)）。

## 結果と代償

- 新しい依存は `go.mod` と lockfile が除外パスなので、同じPRでは自動マージできない。依存を足すPRは人が見る。
- base の `go.mod` を取得できなかったときは、許すと決めずに対象外にする（fail closed）。
- 過去のマージ済みPRには、何もしない。
- 残るリスク: 既存依存の使い方が危うくても、import の検査では止まらない。ほかの規則（認証・DBなどの除外パス）と、人のレビューが受け持つ。
