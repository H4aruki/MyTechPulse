# 本番のGo版への切り替え手順（下書き）

> **この文書は下書きです。** #127 の実施前に、次の「実装が必要な部品」（§3）が出来てから確定します。確定していない箇所は「（案）」と書いています。実施日時、停止の案内、承認者は、オーナーが決めます。

本番のAPIを、Python版からGo版へ入れ替えます。#127 の手順です。本番には既存の利用者のデータがあるため、停止（5〜30分）と切り戻しの条件を決めたうえで行うメンテナンス作業として実施します。

## 1. 何を切り替えるか

接続先のホスト名（`api.mytechpulse.net`）は変えません。同じ名前の裏側で動くものを、画面とセットで入れ替えます。

| 部品 | いま | 切り替え後 | 場所 |
| --- | --- | --- | --- |
| API | Python版 | Go版（manifest で固定した箱） | 本番サーバー（Lightsail） |
| データベース | 3表（`user`、`tag`、`recommend`） | 3表はそのまま。権限の列と、ログイン用の表（`auth_session`）を**追加するだけ** | 本番サーバー |
| 窓口の向け先（Caddy） | Python版（`api:8000`） | Go版（`api-go:8001`） | 本番サーバー |
| 画面 | 旧版（トークン方式） | 新版（Cookie方式。Go版の窓口に合わせて作り直し済み） | Cloudflare Pages |

- **画面とAPIは必ずセットで切り替えます。** 古い画面と新しいAPI、新しい画面と古いAPIの組み合わせは動きません。切り戻しも、画面・API・運用ファイルの組で戻します。
- データベースの変更は追加だけで、Python版はそのまま使えます。切り戻しで、利用者のデータは巻き戻しません。
- ログインの仕組みが変わるため、**切り替え後は、利用者全員が一度ログインし直す**ことになります（旧版のトークンは使えなくなります）。パスワードは変わりません（旧版が作った形式のまま、Go版で照合できることを #126 で確認済み）。

## 2. 前提（#126 の合格の証跡）

- #126 は合成データで合格（2026-10-06・オーナー判定）。
- 切り替えに使う成果物は、**配布元の実行回（run）で作った3つ**（API の箱・画面・運用ファイル）と manifest だけです。本番サーバーで再 build しません。#126 で試した実行回（37420307480）は、手順の確認用です。実際の切り替えには、その時点の `main` から新しく配布を実行し、再度 #126 と同じ手順（箱の中身の確認を含む）で確かめた実行回を使います。
- 合成データでは確かめられなかったこと（実データにだけある変わった値）は、§4 の事前の確認と、§5 の移行前後の内容比較で補います。

## 4. 事前準備（切り替え日までに）

### 4-1. 本番データの事前確認（読み取りだけ・サーバー上）

合成データでは確かめられなかった、実データの変わった値を、先に見つけておきます。

1. タグの衝突の監査（大文字・小文字や前後の空白だけが違うタグが重複していないか）。衝突があると、Go版の登録・タグ処理が正しく動きません。
   ```bash
   docker compose exec -T db psql -X -q -v ON_ERROR_STOP=1 -U postgres -d mytechpulse < ops/sql/audit_tag_collisions.sql
   ```
   `0` なら続行。1以上、または実行できなければ**中止**します。衝突したタグは自動で統合せず、人が決めて、承認を得てから直します。
2. 利用者名の長さ（50文字以内）、パスワードの形式（旧版が作った bcrypt の形式であること）の確認（案。確認用の読み取りSQLを用意する）。

### 4-2. 切り戻し用の保全（G8）

1. いま本番で動いている Python版の箱（image）の識別子と、その運用ファイル一式（`docker-compose.yml`、`Caddyfile`、`ops/`）を、`previous-release.json` が指すフォルダに保全する。
2. 画面（Cloudflare Pages）の、いまの公開の識別子を控える（切り戻しで戻す先）。
3. `previous-release.json` を作る。形式は `ops/deploy_release.sh` の冒頭の説明と、`docs/deploy/go-migration-rehearsal.md` §2-4 のとおり。

### 4-3. 配布と検証

1. 配布を実行する（`release.yml`。外部への送信にあたるので、オーナーの許可が要る）。
2. `docs/deploy/go-migration-rehearsal.md` と同じ手順で、箱の中身（ファイル一覧・環境変数・ビルド履歴）を確認し、manifest の SHA256 を照合する。
3. 本番サーバーで、`ops/deploy_release.sh` を実行して、箱と運用ファイルを準備する（**公開はまだ切り替わらない**）。

### 4-4. 決めること・知らせること

- 実施日時（利用が少ない時間帯）。作業者と承認者。
- 利用者への案内: メンテナンスの日時と、**切り替え後にログインし直すこと**。案内の方法（画面に出す、SNS、など）は未定。
- 中止条件（§5 の判断表）と、切り戻しを決める人。
- 監視の期間（案: 72時間）。

### 4-5. 本番の設定と承認の仕組み

- G7 の設定ファイルをサーバーに置く（オーナー）。
- G6 の `production` 環境と承認者を作る（オーナー）。

- 停止時間の目安: #126 の合成データでは、停止相当が11秒でした。実データの量ではもっと長くなります。**30分を超えそうなら、切り戻しを検討**します。

## 6. 切り戻し

### 切り戻しを決める条件

- 段階3〜9のどれかが失敗した
- 切り替え後、利用者が使えない状態が続く（ログインできない、記事が一切出ない、など）
- 停止時間が30分を超えそう

決める人: 承認者（オーナー）。

### 手順（G4、案）

1. Go版を止める（コンテナを止めるだけ。消さない）。
2. `previous-release.json` が指す旧API（Python版）と運用ファイルの組へ戻し、Caddy の向け先を Python版へ戻す。
3. 画面を、控えておいた直前の公開へ戻す（Cloudflare Pages）。
4. 稼働確認（Python版でログイン、記事一覧）。
5. メンテナンス解除。

- **データベースは巻き戻しません。** Go版が追加した列と表は、Python版が無視します。切り替え中に受け付けた書き込みも失いません（Go版で登録した利用者も、Python版で同じパスワードでログインできます。Go版が作るパスワードの形式 `$2a$10$…` を、Python版の照合処理で正しく読めることを、日本語を含むパスワードで確認済みです）。
- 破壊的な `down` のマイグレーションは使いません。

## 7. 切り替え後の監視（案: 72時間）

- 1時間後、翌日、72時間後に、エラー、サーバーの余裕（メモリ・ディスク。本番は1GBのプランです）、記事一覧の応答、ログインの成否を確認し、#127 に結果だけを記録する。
- 異常があれば §6 の判断。
- 安定を確認したら、#128（Python版の削除）の議論に進む。削除は、対象・役割・影響を示してオーナーの許可を得てから行う。
