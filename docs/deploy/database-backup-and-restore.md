# データベースのバックアップと復元手順

MyTechPulseのデータベース（PostgreSQL 17）を、安全にバックアップし、別の新しいデータベースへ復元して中身を確かめるための手順。Go版への切り替え（#116）の前後で使う。

- 対象: `mytechpulse` データベースの3表（`user`、`tag`、`recommend`）
- すべて**リポジトリのルート**で実行する
- どの手順も既存のデータベース・バックアップを削除しない
- パスワードや実際のバックアップの中身を、チャット・Issue・ログへ貼らない

## 全体の流れ

`準備 → タグ衝突の監査 → 取得 → チェックサム確認 → 新規DBへ復元 → 制約・件数の確認 → 合成データの書き込み確認 → 結果の記録`

途中で1つでも失敗したら、そこで止める。次の段階へ進まず、原因を調べる。

## 1. 準備

```bash
docker compose up -d db
docker compose ps db
```

`db` が `healthy` であることを確認する。本番サーバーのパスワードが必要な場合は、環境変数 `POSTGRES_PASSWORD` に設定する（値は記録しない）。

## 2. タグ衝突の監査

大文字小文字や前後の空白だけが違うタグが重複していないか調べる。衝突があるとGo版の会員登録・タグ処理が正しく動かない。

```bash
docker compose exec -T db psql -X -q -v ON_ERROR_STOP=1 -U postgres -d mytechpulse < ops/sql/audit_tag_collisions.sql
```

- `0` が表示されて終了コード0なら続行してよい
- 1以上、または実行できなかったときは**中止**する
- 中止した間は、Go版の認証（#121）と推薦（#123）の作業を始めない
- 衝突したタグは自動で統合しない。どう直すかは人が決め、承認を得てから修正し、もう一度この監査を実行する

## 3. 取得

```bash
dump_path="$(./ops/backup_db.sh | tail -1)"
echo "$dump_path"
```

`backups/mytechpulse_日時.dump` と、確認用の `.sha256` ファイルが新しく作られる。同名のファイルがすでにあれば上書きせずに止まる。

取得と検証に成功した後、**7日を超えた古い世代が自動で削除される**（`ops/prune_backups.sh`。下の「古い世代の自動削除」を参照）。

## 4. チェックサムの確認

```bash
./ops/verify_backup.sh "$dump_path"
```

`OK: backup verified` が出れば合格。ファイルの大きさだけで成功とは判断しない。

## 5. 新しいDBへ復元

```bash
./ops/restore_db.sh "$dump_path" mytechpulse_restore_issue119
```

- 復元先の名前は `mytechpulse_restore_` で始める。それ以外は拒否される
- 復元先がすでにあるときは上書きせずに止まる。別の名前を付ける
- 復元後、元のデータと復元したデータの内容が一致するかも自動で比べる

## 6. 制約・件数の確認と合成データの書き込み確認

```bash
./ops/verify_restored_db.sh mytechpulse_restore_issue119
```

次を確認する。

- 3表の列、主キー、一意の制約、外部キー、連動して消える設定（CASCADE）が復元されている
- 利用者・タグの番号を数える仕組み（シーケンス）が、最大の番号より先を指している
- 合成データの利用者・タグを追加しても、既存の番号とぶつからない（確認後は元に戻すので、復元DBは変化しない）

`OK: restored database verified` が出れば合格。

## 7. 結果の記録

PRまたはIssueに、次だけを書く。

- 実行日、バックアップのチェックサム（先頭16文字程度）
- 各手順が成功したか
- 失敗した場合は、止まった手順と画面に出たエラーの要点（パスワードや接続情報は除く）

## 新しいスキーマ管理（goose）の扱い

Go版は、起動前に `server/db/migrations/` のSQLを順に適用してDBの構造を管理する。

- `00001_legacy_baseline.sql` は、現行の3表を「出発点」として登録する
  - **空のDB**: 3表を作る
  - **現行と完全に同じ構造の既存DB**: 何も変更せず、構造が一致することだけ確認して記録する
  - **一部だけある、または列・制約が違うDB**: `legacy schema mismatch` で止まる。DBは変更されない
- 適用に失敗したときは、先へ進まずに原因を調べる。本番では適用前に必ず「3. 取得」から「4. チェックサムの確認」までを済ませておく
- 確認コマンド（開発用DBで空のDBを自動作成して試す）:

```bash
cd server
TEST_DATABASE_URL='postgresql://postgres:postgres@127.0.0.1:5432/postgres' go test ./db/migrations -v
```

## バックアップに含まれないもの

`pg_dump` は3表のデータと構造だけを保存する。次は含まれないので、別に再現できるようにしておく。

- データベースのロール（ユーザー）とそのパスワード
- 環境変数の値（項目名は各 `.env.example` を参照）
- Dockerのボリュームそのもの
- Caddyの設定と証明書

## 古い世代の自動削除

`ops/backup_db.sh` は、バックアップの取得と検証に成功した後だけ、`ops/prune_backups.sh` で古い世代を削除する（既定は7日。環境変数 `RETENTION_DAYS` で変えられる）。自動デプロイの前のバックアップでも同じ。

- 消すのは、`backups/` の直下の `mytechpulse_*.dump` と、その `.sha256` だけ
- 次のときは、何も消さない
  - 新しいバックアップが検証を通らなかったとき
  - 7日以内の新しいバックアップが1つも無いとき
  - 同じ名前に `.keep` を付けたファイルがあるとき（例: `mytechpulse_X.dump.keep`。空のファイルでよい）
- 残したいバックアップ（切り替え直前のもの、大きな変更の直前のものなど）には、`touch <ファイル名>.keep` で印を付ける
- 試験: `bash ops/tests/test_prune_backups.sh`

## 本番サーバーの外への保存について

本番サーバーが壊れても復元できるよう、バックアップは別の保存先へ退避する必要がある。ただし次はオーナーの承認が出るまで**実行しない**。

- 外部保存先の決定（保存先、公開範囲、暗号化、費用、保存期間）

承認後、承認済みの環境で「5. 新しいDBへ復元」と「6.」が成功することを、人が確認する。
