# Go版の自動デプロイ

`main` に取り込まれると、検査が全部成功したあと、自動で本番のGo版APIと画面を新しい版に入れ替えます（#125）。人の承認は挟みません（2026-10-07 オーナー決定）。

- **スイッチが入っているときだけ動きます。** リポジトリ変数 `GO_DEPLOY_ENABLED` が `true` のときだけです。未設定・空・`false` では、何も動きません。
- **入れ替えに失敗したら、自動で直前の版へ戻ります。** 利用者のデータは巻き戻しません。

## 1. 流れ

`ci.yml` の次のjobが、順に動きます。どれかが失敗すると、以降は動きません。

| job | 内容 |
| --- | --- |
| 検査（既存の6つ） | 書き方チェック、Go・画面の試験、生成物の差分、箱の検査。全部成功が前提 |
| `deploy-changes` | 変更されたファイルから、本番への反映が要るかを判定する。**文書・試験だけの変更では反映しません**（`scripts/deploy-needed.mjs`）。比較できないときは、安全側に倒して反映する |
| `go-release` | 配布物（Go版の箱・画面・運用ファイル・manifest）を作る（`release.yml` を呼ぶ）。箱は同じ箱を一度だけ作り、digestで固定する |
| `go-deploy` | 配布物をmanifestのSHA256と照合し、本番サーバーへ送って入れ替え（`ops/deploy_go.sh`）、成功したら画面を公開する |

`go-deploy` は、同時に2つ動きません（後から来たものは待ちます）。

### サーバーでの入れ替え（`ops/deploy_go.sh`）

1. 同時実行の防止（ロック）
2. 入力の確認（配布物のSHA256、実行するスクリプトが照合した配布物と同じ中身であること）
3. いま動いているGo版の記録（これが戻し先）
4. 配布物の検証と展開、新しい箱の取得
5. DBのバックアップ
6. DBの移行（追加だけ。入れ替えより先。失敗したら入れ替えない）
7. 入れ替えと、疎通確認（APIの待ち受けと、窓口経由）

7が失敗したら、確認なしで直前の箱へ戻し、戻した後の疎通も確認します。戻すことにも失敗した場合（終了コード4）は、サーバーで状態を確認します（§4）。

### 画面の公開

APIの入れ替えが成功したときだけ行います（画面が新しいAPIを前提にしているため）。公開前の識別子（画面の切り戻し先）が、結果のページ（Summary）に出ます。

## 2. 止めたいとき

次のどちらかで、自動デプロイが止まります。

- リポジトリ変数 `GO_DEPLOY_ENABLED` を削除する、または `false` にする（Settings → Secrets and variables → Actions → Variables）。
- 動いている実行を止めるときは、Actions の該当の実行を「Cancel workflow」する。**入れ替えの途中で止めると、中途半端な状態が残る可能性があります**。サーバーで状態を確認してください（§4）。

## 3. 有効にする（オーナーの作業）

次を確認してから、リポジトリ変数 `GO_DEPLOY_ENABLED` を `true` で作ります。

1. 切り替え後の監視（1時間後・翌日・72時間後）で、問題が無いこと。
2. 次の秘密が、リポジトリのSecretsにあること（旧自動デプロイで使っていたものと同じ）。値は、この文書やリポジトリに書きません。
   - `LIGHTSAIL_SSH_KEY`、`LIGHTSAIL_HOST`、`LIGHTSAIL_USER`（サーバーへの接続）
   - `CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`（画面の公開）
3. サーバーに次があること。
   - `~/releases`（配布物の置き場。切り替えの準備で作成済み）
   - `~/mytechpulse-production.env`（Go版の設定ファイル。切り替えの準備で作成済み）
   - `~/MyTechPulse/ops/backup_db.sh`、`verify_backup.sh`（バックアップ用。**#128 で旧運用ファイルを整理するときに、置き場所を見直す**）
4. 最初の自動デプロイは、小さな変更（例: 画面の文言）で試す。

## 4. うまくいかなかったとき

| 症状 | 見るところ |
| --- | --- |
| `go-deploy` が失敗し、「直前の箱へ戻しました」と出ている | 戻っています（本番は旧版のまま動いています）。失敗の原因は、「サーバーでGo版を入れ替える」の出力（`deploy:` で始まる行）。直してから、もう一度 `main` に取り込む |
| 「直前の箱へ戻すことにも失敗」（終了コード4） | **本番が止まっている可能性があります。** サーバーにログインして `docker ps` と `docker logs` で状態を確認し、Go版が動いていなければ、直前の箱で起動し直す（直前の箱の識別子は、実行の出力の「直前の箱（戻し先）」に出ています） |
| 画面の公開だけが失敗した | APIは新しい版に入れ替わっています。画面は、`gh workflow run cutover-frontend.yml -f action=publish …`（配布の実行回のIDとManifest SHA256を指定）で出し直すか、Cloudflare の管理画面で操作する |
| 「別のデプロイが実行中」 | 前の入れ替えが終わるのを待つ。サーバーで `deploy_go.sh` が動いていないのに出るときは、`~/releases/.deploy.lock.d` が残っている（`flock` が無い環境のみ）。中身が空のディレクトリなので、確認して削除する |

### 画面だけを戻したいとき

```bash
gh workflow run cutover-frontend.yml -R H4aruki/MyTechPulse -f action=rollback
```

## 5. 守っている決まり

- DBの変更は、**追加だけ**にする（列・表の削除や型変更をしない）。入れ替えに失敗して直前の版へ戻ったとき、DBは巻き戻らないため、直前の版が新しいDBでも動く必要があります。
- サーバーで、ソースから再ビルドしない。CIで検査した同じ箱（digest固定）だけを起動する。
- 自動デプロイが作る、受け渡し用の作業場所（`~/deploy-in`・`~/deploy-boot`）だけを、毎回作り直す。DB・バックアップ・配布物の置き場（`~/releases`）は消さない。
