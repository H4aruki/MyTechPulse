# API詳細: おすすめ記事の取得

[API一覧に戻る](../ApiList.md) ／ 共通の取り決めは[APIの共通の決まりごと](../ApiCommonRules.md)を参照

## A-4-1 おすすめ記事の取得

ログイン中の利用者の興味に合う記事をQiita・Zennから集めて返す。このアプリの中心となる窓口。

| 項目 | 内容 |
| --- | --- |
| 方式・パス | GET `/api/v1/feed` |
| 本人確認 | 必要（Cookie） |
| 対応する機能 | F-4-1〜F-4-4（記事の取得・絞り込み・並べ替え・提供元ごとの表示）、F-4-7（Zennが0件のときの補完） |
| 送るもの | なし（誰の記事かはセッションから判断する） |

### 返るもの

| ステータス | code | 意味 |
| --- | --- | --- |
| 200 | ― | 成功。片方の提供元だけ失敗した場合や、記事が0件の場合も200で返す（下の`warnings`で区別する） |
| 401 | `unauthenticated` | ログインしていない、またはセッションの期限切れ |
| 503 | `providers_unavailable` | QiitaとZennの**両方**が使えず、1件も取得できなかった |
| 500 | `internal_error` | サーバー内部の失敗 |

200の本文は次の3項目。

| 項目名 | 型 | 説明 |
| --- | --- | --- |
| qiita_articles | 記事の配列 | Qiitaの記事。点数の高い順に最大10件。該当なしなら空の配列 |
| zenn_articles | 記事の配列 | Zennの記事。点数の高い順に最大10件。該当なしなら空の配列 |
| warnings | 知らせの配列 | 取得に失敗した提供元の知らせ。すべて成功したときは空の配列 |

### 記事1件の中身

| 項目名 | 型 | 説明 |
| --- | --- | --- |
| title | 文字列 | 記事のタイトル |
| url | 文字列 | 記事のアドレス（`https://qiita.com/…`または`https://zenn.dev/…`のみ） |
| source | 文字列 | 提供元（`Qiita` または `Zenn`） |
| tags | 文字列の配列 | 記事に付いているタグ。Zennは、検索に使ったタグだけが入る |
| likes | 数値 | 反響の数（いいね数） |
| published_at | 文字列 | 公開日時（ISO 8601の日時。例: `2026-10-07T01:23:45Z`） |

QiitaとZennで返ってくる形は違うが、サーバー側でこの同じ形に整えてから返している。画面側は提供元を意識せず同じ書き方で表示できる。

### 取得に失敗した提供元の知らせ（warnings）

| 項目名 | 型 | 説明 |
| --- | --- | --- |
| provider | 文字列 | 失敗した提供元（`qiita` または `zenn`） |
| code | 文字列 | 失敗の種類。現在は`provider_unavailable`のみ |

- 片方だけ失敗した場合は、もう片方の記事を返したうえで、失敗した側を`warnings`に入れる。画面側は「一部の記事を取得できませんでした」と知らせる
- 一部のタグだけ失敗した場合も、その提供元は`warnings`に入る。取れた分の記事は返す
- 提供元が返した記事の形が想定と違った（必須項目が無い、アドレスが想定外など）場合も、取得失敗として扱う

### 内部の流れ

記事の集め方は、設定 `ARTICLE_FETCH_ENABLED` で2通りに分かれる。

**記事の一括取得が有効なとき（`true`。本番）**: 1日3回の一括取得でデータベース（`articles`・`article_tags`）に貯めた記事から候補を読む。外部サービスへは問い合わせない。

1. 興味の強さが大きい上位5つのタグを選ぶ（下の手順1と同じ）
2. そのタグが付いた記事を、Qiitaは直近5日以内、Zennは直近14日以内から読む（Zennで14日以内に1件も無いときは、30日以内の古い記事を使う）
3. 下の手順4〜6と同じく、まとめて点数を付け、提供元ごとに上位10件に絞る
4. 提供元ごとに、タグで見つけた記事が10件に満たないときは、タグの数にかかわらず、空いた枠をデータベースの人気の記事で埋める。人気の記事は、いいね数の多い順に20件まで読み（期間は同じで、Zennは14日以内だけ）、すでに選んだ記事を除いてから、タグで見つけた記事と同じ点数で並べ直す（ほかの興味のあるタグが付いた記事が先で、点数0どうしはいいね数の多い順）。タグで見つけた記事を必ず先に並べる
5. Zennの記事にも、データベースの `tag` 表のタグ名が付く
6. データベースの読み出しに失敗したときは、500を返す。外部への即時検索には切り替えない

**記事の一括取得が無効なとき（開発・試験）**: 呼ばれるたびに外部へ問い合わせる（即時検索）。

1. 興味の強さが大きい上位5つのタグを選ぶ（同じ強さなら小文字にそろえた名前の順）。興味の強さが0のタグは選ばない
2. そのタグごとにQiitaとZennへ同時に問い合わせる（[外部サービスへの問い合わせ](../ApiExternal.md)を参照）。全体で8秒を超えたら打ち切る
   - 選べたタグが5つに満たないときは、空いた枠を埋めるため、QiitaとZennへ1回ずつ、タグを問わない人気の記事も問い合わせる。5つ選べたときは問い合わせない
3. Qiitaは直近5日以内、Zennは直近14日以内の記事に絞る
4. 同じ記事（同じアドレス）は1件にまとめ、タグを合わせる
5. 利用者が持つ**すべて**の興味タグを使って点数を付け、並べ替える
6. 提供元ごとに上位10件ずつ返す

### 点数の付け方

| 提供元 | 点数 |
| --- | --- |
| Qiita | 記事に付いたタグの興味の強さの合計 × （いいね数＋1） |
| Zenn | 記事に付いたタグの興味の強さの合計のみ |

- 点数が同じときは、新しい記事、提供元名、アドレスの順で決め、毎回同じ並びになるようにしている
- 点数が0の記事（興味のあるタグが1つも付いていない人気の記事など）どうしは、まずいいね数の多い順に並べる。そのため、人気の記事は、興味のあるタグの記事の後ろに、いいねの多い順で並ぶ
- 即時検索では、Zennの人気の記事にはタグが付かない（[外部サービスへの問い合わせ](../ApiExternal.md)を参照）。そのため、押してもクリック学習には使われない（画面はタグが空のまま送り、[記事クリックの記録](Article.md)はタグ1件以上を求めるので422で断る）
- Zennは興味の強さの合計だけで並べる。いいね数を掛けない理由は、IssueやPRのコメントには残っていません。移行設計（`docs/superpowers/specs/2026-09-14-go-backend-migration-design.md`）には「提供元側の並び順を利用するため」とあります（実装は [PR #145](https://github.com/H4aruki/MyTechPulse/pull/145)）
- タグを突き合わせるときは、前後の空白を除いて、大文字・小文字の違いを無視して比べている

### 記事が集まらなかったときの動き

次の表は即時検索のときの動き。一括取得が有効なときは、[内部の流れ](#内部の流れ)のとおり、提供元ごとにタグで見つけた記事が10件に満たなければ人気の記事で埋め、外部の失敗による503は起きない（データベースの失敗は500）。

| 状況 | 動き |
| --- | --- |
| 興味の強さが0より大きいタグが5つに満たない | 空いた枠を、タグを問わない人気の記事で埋める（提供元ごとに1回だけ問い合わせを足す） |
| 興味の強さが0より大きいタグを1つも持っていない | 人気の記事だけを返す |
| タグで見つけたZennの記事が14日以内に1件も残らなかった | 問い合わせを増やさずに、すでに取得した結果から期間の条件だけを外して埋め合わせる（人気の記事は14日以内のものだけ使う） |
| Qiita・Zennの両方が0件（失敗ではない） | 両方とも空の配列で200を返す。画面側は「おすすめの記事はまだありません。」と表示する |
| 両方の提供元が失敗した | 503（`providers_unavailable`）を返す。画面側は再読み込みを案内する |

### 補足

- 即時検索では、記事はデータベースに保存しておらず、この窓口が呼ばれるたびに外部へ取りに行く。そのため表示までの待ち時間は外部サービスの応答速度に左右される
- 一括取得が有効なときは、あらかじめ集めてデータベースに貯めた記事を読む（機能一覧のF-4-10。`server/internal/articlefetch/`、[Issue #66](https://github.com/H4aruki/MyTechPulse/issues/66)）。進捗はリポジトリ直下の`TASKS.md`で管理している
- 同じ利用者の過去の閲覧は、記事のデータとしては保存していない。保存しているのはタグごとの興味の強さだけ
- 旧版（Python）にあった「本文の`status`で0/1を返す」決まりは、なくなった。成否はHTTPステータスで見る
