# 外部サービスへの問い合わせ

サーバーが記事を集めるために呼び出している、外部（Qiita・Zenn）の窓口をまとめたもの。ここは自分たちが提供する窓口ではなく、相手先の仕様に合わせて呼び出している部分になる。

呼び出しが起きるのは[おすすめ記事の取得（A-4-1）](Details/News.md)のときだけ。実装は`server/internal/provider/`にあり、提供元ごとの違いはこの中に閉じ込めている。

## 1. 問い合わせ先の一覧

| 提供元 | 方式・アドレス | 主な条件 | 認証 |
| --- | --- | --- | --- |
| Qiita | GET `https://qiita.com/api/v2/tags/{タグ名}/items` | 1ページ目・20件 | 利用登録して発行した鍵（`QIITA_ACCESS_TOKEN`）を、`Authorization`の見出しに付けて送る |
| Zenn | GET `https://zenn.dev/api/articles` | タグ名（小文字）を`topicname`で指定・5件 | 不要 |

ZennのAPIは公式に仕様が公開されていないため、応答の項目が欠けたり型が変わったりした場合は「応答が不正」として検出する。RSSなど別の取得方法へは自動で切り替えない。

## 2. 呼び出し方

- 興味の強さが大きい上位5つのタグについて、QiitaとZennの両方へまとめて同時に問い合わせる
- 1回の記事一覧表示あたり、外部への問い合わせは最大10回（5タグ × 2提供元）。再試行が起きたときは、その分だけ増える
- 順番に待たず同時に投げるため、待ち時間は「一番遅い1回」に近い長さで済む

### 時間と大きさの上限

| 項目 | 既定値 | 設定名 |
| --- | --- | --- |
| 1回の問い合わせの待ち時間 | 5秒 | `PROVIDER_TIMEOUT` |
| 記事一覧の取得全体の待ち時間 | 8秒 | `FEED_TIMEOUT` |
| 1回の応答として受け取る大きさ | 約2MB | `PROVIDER_MAX_BYTES` |

## 3. 気をつけている点

| 点 | 内容 |
| --- | --- |
| 接続先の固定 | 接続先は`https`の`qiita.com`と`zenn.dev`に完全一致するものだけ。リダイレクトは追いかけず、受けたら失敗として扱う。鍵を別のサイトへ送ってしまうのを防ぐため |
| タグ名の変換 | タグ名をアドレスに埋め込む前に必ず変換してから送る。`/`や`..`を含むタグでも、意図しない別の窓口へ届いてしまわないようにするため |
| 大文字・小文字 | Zennは小文字でないと記事が見つからないため、送る前に小文字へそろえる |
| タグ情報の補い | Zennの一覧には記事本来のタグが含まれないため、「どのタグで検索して見つかったか」をその記事のタグとして扱う。複数のタグで見つかった記事は1件にまとめる |
| 記事アドレスの検査 | 受け取った記事のアドレスが`https`で、想定のサイトのものかを確かめる。違えば応答不正として扱う |
| 再試行 | 一時的な失敗（時間切れ・接続失敗・502/503/504）だけ、期限内で最大1回やり直す。429（回数制限）やその他の4xxは、やり直さない |

## 4. 失敗したときの扱い

| 状況 | 扱い |
| --- | --- |
| 一部のタグの問い合わせが失敗 | 取れた分の記事は使い、その提供元を「取得できなかった」知らせ（`warnings`）に入れる |
| 片方の提供元がすべて失敗 | もう片方の記事を返し、失敗した側を知らせに入れる |
| 両方の提供元がすべて失敗 | 503（`providers_unavailable`）を返す |

- 失敗の内容には、問い合わせのアドレス、鍵、応答の本文を含めない。分かるのは「どの提供元が、どの種類で失敗したか」だけ
- 失敗が画面に知らされるため、気づかないまま特定の提供元の記事だけが減る、ということは起きにくくなった

## 5. 補足

- Qiitaの鍵は、サーバーの環境設定に置き、リポジトリには含めない。未設定だとサーバーは起動しない
- 記事をあらかじめ集めておく方式に変えれば、この問い合わせは利用者の画面表示とは切り離せる（機能一覧のF-4-10）
