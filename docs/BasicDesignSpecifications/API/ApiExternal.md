# 外部サービスへの問い合わせ

サーバーが記事を集めるために呼び出している、外部（Qiita・Zenn）の窓口をまとめたもの。ここは自分たちが提供する窓口ではなく、相手先の仕様に合わせて呼び出している部分になる。

呼び出しが起きるのは[おすすめ記事の取得（A-4-1）](Details/News.md)のときだけ。実装は`server/internal/provider/`にあり、提供元ごとの違いはこの中に閉じ込めている。

## 1. 問い合わせ先の一覧

| 提供元 | 方式・アドレス | 主な条件 | 認証 |
| --- | --- | --- | --- |
| Qiita | GET `https://qiita.com/api/v2/tags/{タグ名}/items` | 1ページ目・20件 | 利用登録して発行した鍵（`QIITA_ACCESS_TOKEN`）を、`Authorization`の見出しに付けて送る |
| Zenn | GET `https://zenn.dev/api/articles` | タグ名（小文字）を`topicname`で指定・5件 | 不要 |
| Qiita（人気の記事） | GET `https://qiita.com/api/v2/items` | `query=created:>=（5日前の日付） stocks:>=10`・1ページ目・10件 | タグ別と同じ鍵 |
| Zenn（人気の記事） | GET `https://zenn.dev/api/articles` | `order=weekly`（Zennの週間の人気順）・`article_type=tech`・5件 | 不要 |

人気の記事は、興味の強さが0より大きいタグが5つに満たないときだけ使う（[おすすめ記事の取得](Details/News.md)）。

- QiitaのAPIには「いいね数の順」に並べる指定が無く、検索結果は新しい順に返る。そのため、ストック数10以上で反響のあった記事に絞って取り、こちらでいいね数の順に並べる（検索条件の`likes:`は効かない。2026-10-19に確認）
- Qiitaの人気の記事は本文が長く、20件だと応答が約2MBの上限を超えやすいため、10件にしている（2026-10-19の実測で、20件が約2.3MB、10件が約1.2MB）
- Zennの一覧は記事本来のタグを返さないため、人気の記事にはタグが付かない

ZennのAPIは公式に仕様が公開されていないため、応答の項目が欠けたり型が変わったりした場合は「応答が不正」として検出する。RSSなど別の取得方法へは自動で切り替えない。

## 2. 呼び出し方

- 興味の強さが大きい上位5つのタグについて、QiitaとZennの両方へまとめて同時に問い合わせる
- 1回の記事一覧表示あたり、外部への問い合わせは最大10回（5タグ × 2提供元）。再試行が起きたときは、その分だけ増える
- タグが5つに満たないときは、人気の記事の分として提供元ごとに1回ずつ足す（タグがk個なら 2k＋2 回。k≦4 なので最大10回のまま）
- 順番に待たず同時に投げるため、待ち時間は「一番遅い1回」に近い長さで済む

### 時間と大きさの上限

| 項目 | 既定値 | 設定名 |
| --- | --- | --- |
| 1回の問い合わせの待ち時間 | 5秒 | `PROVIDER_TIMEOUT` |
| 記事一覧の取得全体の待ち時間 | 8秒 | `FEED_TIMEOUT` |
| 1回の応答として受け取る大きさ | 約2MB | `PROVIDER_MAX_BYTES` |

## 3. 気をつけている点

| 点 | 内容 |
| --- | --- |
| 接続先の固定 | 接続先は`https`の`qiita.com`と`zenn.dev`に完全一致するものだけ。リダイレクトは追いかけず、受けたら失敗として扱う。鍵を別のサイトへ送ってしまうのを防ぐため |
| タグ名の変換 | タグ名をアドレスに埋め込む前に必ず変換してから送る。`/`や`..`を含むタグでも、意図しない別の窓口へ届いてしまわないようにするため |
| 大文字・小文字 | Zennは小文字でないと記事が見つからないため、送る前に小文字へそろえる |
| タグ情報の補い | Zennの一覧には記事本来のタグが含まれないため、「どのタグで検索して見つかったか」をその記事のタグとして扱う。複数のタグで見つかった記事は1件にまとめる |
| 記事アドレスの検査 | 受け取った記事のアドレスが`https`で、想定のサイトのものかを確かめる。違えば応答不正として扱う |
| 再試行 | 一時的な失敗（時間切れ・接続失敗・502/503/504）だけ、期限内で最大1回やり直す。429（回数制限）やその他の4xxは、やり直さない |

## 4. 失敗したときの扱い

| 状況 | 扱い |
| --- | --- |
| 一部のタグの問い合わせが失敗 | 取れた分の記事は使い、その提供元を「取得できなかった」知らせ（`warnings`）に入れる |
| 片方の提供元がすべて失敗 | もう片方の記事を返し、失敗した側を知らせに入れる |
| 両方の提供元がすべて失敗 | 503（`providers_unavailable`）を返す |

- 失敗の内容には、問い合わせのアドレス、鍵、応答の本文を含めない。分かるのは「どの提供元が、どの種類で失敗したか」だけ
- 失敗が画面に知らされるため、気づかないまま特定の提供元の記事だけが減る、ということは起きにくくなった

## 5. 補足

- Qiitaの鍵は、サーバーの環境設定に置き、リポジトリには含めない。未設定だとサーバーは起動しない
- 記事をあらかじめ集めておく方式に変えれば、この問い合わせは利用者の画面表示とは切り離せる（機能一覧のF-4-10）

## 6. 定期の一括取得（Issue #66 ステップ1。既定は無効）

画面を開いたときの問い合わせとは別に、決まった時刻に記事をまとめて取り、DBへ貯める仕組みを足した。フィード（画面に出す記事）は、まだこのDBを読まない。

`ARTICLE_FETCH_ENABLED=true` のときだけ動く。**既定は `false`（どの環境でも）**。`main` へ反映して本番に入っても動かず、オーナーが本番の設定で `true` にして初めて動く。

| 項目 | 内容 |
| --- | --- |
| 実行の時刻 | 日本時間の 6:00・11:30・16:30。起動時に、直近の取り逃した枠があれば1回だけ補う |
| Qiita | `GET /api/v2/items?query=created:>=日付 created:<翌日`・1ページ20件。保持期間（5日）の分を、日付ごとに、20件に満たないページまで取る。毎回取り直すので、いいね数も更新される |
| Zenn | 取得対象のタグ（`fetch_tags`、上限500件）ごとに1回・5件。同時に2本まで、開始の間隔は0.5秒以上 |
| 呼び出し回数の上限 | Qiitaは1回の実行で300回まで（再試行を含む。`ARTICLE_FETCH_QIITA_MAX_REQUESTS`、最大800）。応答の `Rate-Remaining` が100を下回ったら止める。429を受けたら残りを打ち切る |
| 再試行 | 一時的な失敗（時間切れ・接続失敗・5xx）だけ、1秒・2秒・4秒の待ちで最大3回やり直す（合計4回まで）。4xx・応答不正・429はやり直さない |
| 全体の再実行 | 両方が全滅（またはDBの書き込み失敗）のとき、1回目の失敗の15分後、2回目の失敗の30分後に再実行。次の定時を過ぎる場合は、次の定時に任せる |
| 保存 | `articles`（記事）、`article_tags`（`tag` 表にあるタグだけ。外部のデータから `tag` の行は作らない）。同じ `(source, external_id)` は上書き |
| 保持期間 | Qiitaは公開から5日、Zennは30日。過ぎた記事は毎回の実行の最後に消す |
| 履歴 | `fetch_runs` に、実行の状態・件数・呼び出し回数・失敗の内容を残す。失敗の内容は分類済みの文だけで、URL・鍵・応答の本文は入れない |
| 同時実行 | DBのアドバイザリロック（専用の接続）で、複数のAPIが同時に取得しないようにする |
