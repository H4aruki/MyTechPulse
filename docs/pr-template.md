# PRテンプレートの使い方

`.github/pull_request_template.md` の書き方をまとめる。本文はAIが書く。PR本文は、差分を手元に持つレビュワー向けの「1分で読めるブリーフィング」であり、実験ノートではない。人は差分を全部読まなくても、「なぜ必要か・何を対象外にしたか・何を壊しうるか・どう確かめたか・何を決めるか」を判断できることを目標にする。

テンプレートの6節は、共通テンプレート（`/home/box/shared/pr-template/pull_request_template.ja.md`、pstack poteto-mode の opening-a-pr の日本語訳）をそのまま使う。MyTechPulse が足したのは、末尾の「判断が必要なこと」だけ。経緯は [ADR 0013](adr/0013-pr-template-briefing-with-decision-section.md) を参照する。

## 判断に関わっていない人にも読める書き方

PRも Issue も、本文は、その判断に関わっていない開発者が、会話の履歴を知らなくても読めるように書く。「案A」「v2」のような内側だけの呼び方で済ませず、選択肢の中身と、採らなかった理由を本文で説明する。

## 人が最初に見る順番

1. ボットの判定コメント（自動マージかどうか、引っかかったルール、大きさ）
2. 「判断が必要なこと」。「なし」で判定が対象なら、差分は読まなくていい
3. 必要なら「範囲」「影響範囲」「確認」

## 節の書き方

本文は約40行以内にする（squash コミットの本文になる）。`##` 見出しを使い、次の順に並べる。

| 節 | 書くこと |
|---|---|
| なぜ（Why） | 問題とアプローチを短い文で1〜3文。SHAやリベースの経緯は書かない |
| 何を変えたか（What changed） | 短い箇条書きで1〜3個。名前の変更は変更前と後の両方 |
| 範囲（Scope） | 必須。対象と、あえて対象外にしたこと（後続の作業、分かっている抜け）を1〜3項目 |
| トレードオフ（Tradeoffs） | レビュワーが聞いてきそうな、採らなかった選択肢だけ。無ければ省く。判断に関わっていない開発者でも分かるように、各選択肢の中身と採らなかった理由を本文で書く。内側だけの呼び方（案Aなど）だけで済ませない |
| 影響範囲（Blast Radius） | 誰に・何に影響するか、なぜ安全か・危ないかを1〜2文 |
| 確認（Verification） | 実際に走らせた手順と結果を1〜3個。実行していない検証を成功と書かない |
| 判断が必要なこと | 必須。無ければ「なし」とだけ書く。ある場合は、1つずつ「何を決めるか / 選択肢（表または図） / おすすめと理由」 |

「書くことがない節は消す」は共通テンプレートの規則で、そのまま残している。ただし「判断が必要なこと」は自動マージの判定が見る節なので、消さない。

## 図・動画・スクリーンショット

- 新機能では、構成図やUMLを付けてもよい。必須ではない。構成図は stack-diagram スキルで描き、各節のあとに置く
- 動画やスクリーンショットは、主張の証拠になるときだけ、各節のあとに置く
- 図を置くときは、直後にその図が示すことを1文で書く
- 秘密情報・個人情報・本番の値が写っていたら出さない
- 完全なSHA、ファイルごとのチェックリスト、修正の経緯を語る長文は、本文ではなくリンク先に置く

## 判断が必要なこと

「なし」以外を書くと、自動マージの対象外になる。「なし」以外とは、「なし」に文を足したもの（例: 「なし。ただし要確認」）も含む。他の節に「なし」と書いても、判定には効かない。AIが「なし」に寄せて通そうとしてはいけない。迷いがあれば「なし」にしない。決めるのは人。

## 自動マージとの関係

自動マージの判定は本文を信じない。スクリプトが差分とAPIから決め、結果をボットのコメントに出す。本文からは「判断が必要なこと」の節だけを見て、HTMLコメントを除いた本文が「なし」だけなら通る（`scripts/automerge/eligibility-core.mjs`）。
