# PRテンプレートの使い方

`.github/pull_request_template.md` の書き方と、その理由をまとめる。本文はAIが書く。人は差分を全部読まなくても、図と証拠で「正しいか・意図どおりか・何を決めるか」だけ判断できることを目標にする。

## 人が最初に見る順番

1. ボットの判定コメント（自動マージかどうか、引っかかったルール、大きさ）
2. 「判断が必要なこと」。「なし」で判定が対象なら、差分は読まなくていい
3. 必要なら「理解しておいてほしい1点」の図と、「確かめたこと」のスクショや表

## 図と画像の規則

- 文章だけで済ませず、図か画像を先に置く
- 動く部分が3つ以上ある流れは、1枚に詰めず短いシリーズにする
- 挙動は mermaid（flowchart か sequence）、状態は状態図、画面は before / after のスクショ、操作は短い動画
- 図の直後に、その図が示すことを1文で書く
- スクショは実際の画面。モックや想像図は「参考」と明示する
- 無いときは「なし」と理由を1行書く。空欄は不可
- 秘密情報・個人情報・本番の値が写っていたら出さない

## 各節の書き方

節の順番は変えない。

| 節 | 書くこと | 置く図 |
|---|---|---|
| 一行で | 利用者から見た変化を1文 | 画面なら before / after の小さな画像。API は入出力の mermaid 1枚 |
| なぜ | `Refs #` と、起きたこと | 流れやタイミングのバグなら、壊れていた流れの mermaid 1枚 |
| 理解しておいてほしい1点 | 仕組みの肝を1つだけ。図を先に、本文は1〜2文 | 流れ: flowchart / sequence。状態: stateDiagram。画面: 注釈つきスクショ |
| 確かめたこと | コマンドと結果、テスト表 | 画面は before / after、操作は短い動画 |
| 判断が必要なこと | 何を決めるか、選択肢、おすすめと理由 | 案ごとにサムネか mermaid |
| 見てほしい場所 | `path:start-end` を最大3つ | 1箇所なら短い引用（10行以内） |
| 確認 | チェック2つ | なし |

## 証拠の規則

- 「直した」だけの自己申告は不可
- 直す前に落ちて、直した後に通るテストを表にする（ケース / 直す前 / 直した後 / 証拠）。書けないなら理由を1行書く
- 画面の変更は before / after のスクショ、操作の変更は短い動画
- 実行コマンドは、コピーして再実行できる形で書く
- 「全部通った」と列挙だけで書かず、ケースを表に落とす

## 判断が必要なこと

「なし」以外を書くと、自動マージの対象外になる。AIが「なし」に寄せて通そうとしてはいけない。迷いがあれば「なし」にしない。決めるのは人。

## 自動マージとの関係

自動マージの判定は本文を信じない。スクリプトが差分とAPIから決め、結果をボットのコメントに出す（判定スクリプトは別のPRで入る）。
